# 第 4 篇：SPI / QSPI 屏——从发送命令到局部刷新

> 系列：[从点亮屏幕到高性能 GUI：i.MX RT 图形系统实战](README.md)
>
> 上一篇：[选屏之前，先算清分辨率、显存与带宽](03-memory-and-bandwidth.md)
>
> 本篇目标：理解带 GRAM 串行屏的命令与像素传输，建立正确的区域更新、DMA 和异步缓冲区交接流程。
>
> 适用条件：以常见四线 SPI、8 位命令、RGB565 区域写入为讲解模型。命令示例采用常见的 `0x2A / 0x2B / 0x2C` 语义；不是所有面板的通用初始化代码。QSPI 部分介绍匹配方法，不预设具体屏幕与主控组合。
>
> 验证边界：本文给出协议示例、离线可执行的字节序脚本和板级实验方法；未声称已经在特定开发板上运行，也没有填写未经测量的板卡性能。

## 1. 串行屏的优势，不只是引脚少

在[第 3 篇](03-memory-and-bandwidth.md)中，我们看到，单线 SPI 的整屏传输能力有限。

但这不等于 SPI 屏不适合 GUI。

对数值、菜单和状态界面而言，大部分画面可能不需要持续改变。此时，带 GRAM 的串行屏可以把完整画面留在屏幕端，主控只更新变化区域。

典型路径是：

```text
CPU / GUI 绘制
      |
      v
局部像素缓冲区
      |
      v
SPI / QSPI 传输
      |
      v
屏幕控制器与 GRAM
      |
      v
面板扫描
```

这类架构把“生成新的像素”和“持续扫描已有画面”分开。

主控侧不一定需要保存整屏内容，也不一定每个扫描周期都发送整屏像素。

真正需要解决的是：

1. 屏幕怎么区分命令和数据？
2. 像素应该写进哪个区域？
3. 数据的格式、顺序和数量是否正确？
4. 什么时候可以重新使用发送缓冲区？

## 2. 先弄清楚你买到的是哪种 SPI 屏

商品页面写着“SPI”，信息仍然不够完整。

至少应确认：

- 显示控制器型号和模组版本。
- 实际采用的接口模式。
- 数据位数、时钟模式和允许速率。
- 逻辑分辨率、控制器 GRAM 尺寸和显示区域偏移。
- 支持的像素格式。
- 命令 / 数据区分方式。
- 复位、背光与 TE 等辅助信号。

### 2.1 常见四线 SPI

一种常见连接方式如下：

| 信号 | 作用 |
| --- | --- |
| SCLK | 串行时钟 |
| MOSI / SDI | 主控发送命令、参数和像素 |
| CS | 片选，限定事务边界 |
| D/C | 区分命令与数据 |
| RESET | 屏幕控制器复位 |
| BL | 背光控制，可能通过驱动电路实现 |
| MISO / SDO | 可选读取路径，模组不一定引出 |
| TE | 可选扫描同步输出 |

“四线 SPI”中的接口命名通常围绕时钟、数据、片选和 D/C，但不同厂商可能采用不同计数习惯。不能据此推断模组总共只需要四根连线。

在常见约定中，D/C 为低表示命令，为高表示参数或像素；实际极性仍应以控制器和模组资料为准。

MISO 与 MOSI 同时存在，也不代表像素写入吞吐自动翻倍。主控写像素使用的是实际输出数据路径。

### 2.2 三线或带命令位的串行模式

有些模式通过每个传输字中的额外位来表示命令 / 数据，例如 9 位传输。

这时需要核对：

- SPI 控制器是否支持所需字长。
- DMA 如何排列传输字。
- 额外命令位如何计入吞吐。
- 驱动是否按这个模式组织事务。

不能直接把四线 SPI 的 8 位字节流驱动套过去。

### 2.3 多数据线 QSPI

QSPI 通常表示像素数据阶段可以使用多条数据线，但具体事务未必完全相同。

有些协议的命令、地址、参数与像素阶段使用不同线宽，或者要求特定的包头和转换过程。

这部分会在后面单独展开。

## 3. 软件结构分成三层，更容易移植

不要把面板寄存器、SPI 驱动和 LVGL 回调全部写在一个函数里。

可以沿用 SDK 已有的分层方式，理解为三个职责：

| 层次 | 负责什么 | 不应负责什么 |
| --- | --- | --- |
| 板级初始化 | 电源、引脚、时钟、复位、背光 | 不处理控件和无效区域 |
| 面板驱动 | 初始化命令、方向、像素格式、地址窗口 | 不假设某个 GUI 框架的对象结构 |
| 传输接口 | 命令 / 数据发送、DMA、完成与错误通知 | 不决定页面内容 |

GUI 显示端口在这些层次之上，把待更新区域和像素交给面板与传输层。

在 NXP 公开组件中，可以看到面板组件通过 DBI 接口进行命令、数据和内存写入。这类已有组件应作为优先检查的起点，不应为了文章示例另造一套重复驱动。

但组件存在不等于板级条件已经满足。仍要核对当前 SDK 的版本、接口形式和目标屏幕初始化。

## 4. 初始化：先让控制器进入正确状态

串行屏初始化通常涉及：

1. 确认供电和逻辑电平。
2. 初始化主控引脚与传输外设。
3. 根据模组要求执行复位。
4. 发送目标模组要求的初始化序列。
5. 配置像素格式、方向和可见区域。
6. 按规定等待相关状态转换。
7. 开启显示，并根据硬件方案控制背光。

其中可能出现退出睡眠、显示开关、扫描方向、Gamma 和电源参数等命令。

但这些参数不是通用常量。

即使两个模组使用同一型号控制器，也可能因为面板、电源和可见区域不同，需要不同参数。

因此，本篇不提供一份“适用于所有 SPI 屏”的初始化数组。正确起点应是：

- 模组厂商的初始化说明。
- 对应控制器资料。
- SDK 中针对相同模组的组件与示例。

初始化阶段先使用保守的、资料允许的时钟进行验证，再逐步评估更高频率。不要把其他板卡能工作的超规格速率当作设计依据。

## 5. 地址窗口：告诉屏幕这批像素写到哪里

许多常见控制器支持以下语义：

| 命令 | 常见功能 |
| --- | --- |
| `0x2A` | 设置列地址范围 |
| `0x2B` | 设置行地址范围 |
| `0x2C` | 开始写入像素数据 |

这里采用：

- 起止坐标都是包含端点的范围。
- 坐标参数为高字节在前的 16 位数。
- 每个 RGB565 像素发送两个字节。

这些假设需要在目标控制器上确认。

### 5.1 一个具体区域

假设逻辑分辨率为 320 × 240，方向已正确设置，且本例没有额外 GRAM 偏移。

更新区域：

```text
x = 20
y = 30
width = 100
height = 40
```

那么：

```text
x_start = 20
x_end = 20 + 100 - 1 = 119
y_start = 30
y_end = 30 + 40 - 1 = 69
```

对应事务内容：

```text
D/C = 命令：2A
D/C = 数据：00 14 00 77

D/C = 命令：2B
D/C = 数据：00 1E 00 45

D/C = 命令：2C
D/C = 数据：接下来的像素字节流
```

像素数量和字节数为：

```text
100 × 40 = 4,000 pixel
4,000 × 2 = 8,000 B
```

这里只展示命令和数据内容。CS 是否保持、什么时候可以切换 D/C、允许怎样拆分事务，应按控制器和主控传输规则执行。

### 5.2 最容易出现的边界错误

| 错误 | 结果 |
| --- | --- |
| 结束坐标写成 `x + width` | 比预期多一列 |
| 传输长度按像素数而不是字节数填写 | RGB565 数据可能只发送一半 |
| 忽略模组可见区域偏移 | 图像位置整体错误 |
| 旋转后仍使用原坐标映射 | 方向、范围或扫描顺序错误 |
| 截断了窗口，却没有同步调整源图像 | 目标范围和源像素不对应 |

区域校验不应只做一个“越界就返回”的静默分支。

驱动或端口应使用项目既有的错误通道，明确记录请求范围、屏幕范围和源缓冲条件，并把失败交给上层处理。

## 6. 同样叫 RGB565，字节顺序也可能不同

RGB565 的红色可以表示为：

```text
0xF800
```

在常见小端 CPU 内存中，这个 16 位数的两个字节通常是：

```text
00 F8
```

如果目标屏幕要求先发送高字节，链路上的顺序应为：

```text
F8 00
```

两者的像素含义相同，但直接按内存字节发送可能不符合屏幕要求。

### 6.1 三种不同问题不要混在一起

1. **RGB / BGR：** 红蓝通道映射或配置不同。
2. **像素字节顺序：** 一个 16 位像素的高低字节顺序不同。
3. **单个字内位顺序：** SPI 字传输采用 MSB-first 或 LSB-first。

把 SPI 配成 MSB-first，不自动解决“以 8 位 DMA 发送小端 16 位数组”的像素高低字节问题。

正确做法需要结合 SPI 帧宽、DMA 宽度和驱动对内存的读取方式。

### 6.2 可考虑的处理方式

- 如果硬件与驱动支持合适的 16 位发送行为，利用它生成所需顺序。
- 使用专门的发送缓冲区进行字节重排。
- 在满足刷新模式与生命周期要求时，使用所选 GUI 版本提供的字节交换辅助逻辑。

不要未经分析就原地修改长期保存的帧缓冲区。

如果后续绘制仍把该内存当作原生像素格式使用，原地交换可能破坏下一轮绘制或导致重复交换。

有独立发送缓冲区时，可以保留源图像格式，但要把额外转换、容量和内存读写计入预算。

### 6.3 最小颜色验证

在本例“高字节先发”的假设下：

| 颜色 | RGB565 数值 | 链路字节 |
| --- | --- | --- |
| 红 | `0xF800` | `F8 00` |
| 绿 | `0x07E0` | `07 E0` |
| 蓝 | `0x001F` | `00 1F` |
| 白 | `0xFFFF` | `FF FF` |
| 黑 | `0x0000` | `00 00` |

测试图案最好包含彩色和位置变化，而不只是黑白。黑白在字节交换后数值不变，不能充分暴露 RGB565 高低字节问题。

## 7. 区域像素不一定在内存中连续

假设一张完整源图像宽度为 320，RGB565，紧凑行跨度为 640 B。

从中取出宽度 100 的区域，每行只需要发送 200 B。

区域的下一行通常不是紧跟着这 200 B，而是要从源图像的下一行相同横坐标读取：

```text
source_row(y) = source_base + y × source_stride + x × 2
```

如果直接从起始地址连续发送 `100 × 40 × 2` 字节，就会把区域右侧的其他像素也发送出去。

常见处理方案包括：

1. GUI 本来就生成紧凑排列的局部缓冲区。
2. 按行发送源图像的目标区域。
3. 把各行打包进连续发送缓冲区。
4. 在硬件和驱动允许时使用分散 / 聚集等传输能力。

每种方案都有成本：

- 按行发送可能增加事务或调度间隔。
- 打包增加额外内存读写和缓冲容量。
- 高级 DMA 描述符需要核对硬件限制。

如果把一块窗口拆成多段像素传输，还必须确认屏幕是否允许中断后继续写入、CS 边界是否改变写入状态，以及是否需要专用续写命令。

不能默认“下一次 DMA 会从上次窗口位置继续”。

## 8. 先建立阻塞正确基线，再引入 DMA

第一次点亮串行屏，建议先验证一条简单而明确的同步路径：

```text
校验区域和源图像
      |
      v
取得屏幕 / 总线的独占访问
      |
      v
设置列窗口、检查结果
      |
      v
设置行窗口、检查结果
      |
      v
开始像素写入、检查结果
      |
      v
发送正确字节数的像素
      |
      v
确认事务按硬件语义结束
      |
      v
释放访问并报告结果
```

任何一步失败，都进入明确的错误收尾流程：

- 停止继续提交像素。
- 按传输接口约定终止或恢复事务。
- 记录错误与当前状态。
- 确认没有消费者继续使用源缓冲区。
- 释放资源，向上层报告失败。

不要在命令发送失败后继续像什么都没发生一样写像素。

同步路径的价值不是追求最高性能，而是建立一个可观察的参考结果。

这个基线至少应通过：

- 纯色。
- 色条。
- 四角标记。
- 指定窗口更新。
- 变化区域之外的旧画面保持不变。

通过之后，再把像素传输替换为 DMA。

## 9. 一个可以离线复算的窗口写入示例

下面的 Python 脚本只生成本篇示例的命令内容和 RGB565 字节流，不访问 SPI，也不模拟硬件完成。

它使用标准库语法，无需第三方依赖。

```python
screen_width, screen_height = 320, 240
x, y, width, height = 20, 30, 100, 40

if not (
    width > 0
    and height > 0
    and 0 <= x <= screen_width - width
    and 0 <= y <= screen_height - height
):
    raise ValueError("The requested rectangle is outside the logical display.")

column_command = b"\x2a" + x.to_bytes(2, "big")
column_command += (x + width - 1).to_bytes(2, "big")
row_command = b"\x2b" + y.to_bytes(2, "big")
row_command += (y + height - 1).to_bytes(2, "big")

red_pixel = (0xF800).to_bytes(2, "big")
pixel_payload = red_pixel * (width * height)

print("Column:", column_command.hex(" ").upper())
print("Row:", row_command.hex(" ").upper())
print("Memory write: 2C")
print(f"Pixel payload: {len(pixel_payload):,} B")
print("First two pixels:", pixel_payload[:4].hex(" ").upper())
```

对应输出：

```text
Column: 2A 00 14 00 77
Row: 2B 00 1E 00 45
Memory write: 2C
Pixel payload: 8,000 B
First two pixels: F8 00 F8 00
```

移植到板卡后，需要把命令首字节和后续参数按 D/C 规则分别发送，再执行像素写入事务。脚本中的拼接只表达逻辑内容，不意味着可以把整段数组在 D/C 固定不变时直接发给四线 SPI 屏幕。

## 10. DMA 的收益与边界

DMA 可以把数据从源内存送到 SPI 发送路径，使 CPU 不必逐字节等待。

典型路径是：

```text
RAM -> DMA -> SPI 发送 FIFO / 移位器 -> 屏幕
```

它的主要收益是：

- 降低 CPU 搬运开销。
- 减少软件造成的传输间隔。
- 为绘制与传输重叠创造条件。

但 DMA 不会把固定时钟下的单线传输变成四线传输，也不会突破屏幕允许的时序。

### 10.1 启动 DMA 前核对什么？

| 项目 | 核对内容 |
| --- | --- |
| 地址 | DMA 能否访问源缓冲区所在区域 |
| 长度 | 驱动参数是字节、传输字还是其他单位 |
| 宽度 | DMA 访问宽度与 SPI 帧宽如何配合 |
| 格式 | 像素字节顺序是否已经满足要求 |
| 对齐 | 源地址、长度和硬件限制 |
| Cache | CPU 写入的数据是否已对 DMA 可见 |
| 生命周期 | 传输结束之前，源缓冲区是否保持有效且不被修改 |
| 总线 | 命令、窗口与像素是否属于同一受控访问过程 |

CPU 在可缓存内存中生成像素，DMA 从非一致性路径读取时，可能需要按目标 SDK 和缓存行规则执行 Clean。

不能简单把“关闭 Cache”当作所有平台的最终优化方案，也不能随意对包含其他数据的缓存行做维护。

具体一致性细节会在后续 Cache 章节展开。

### 10.2 DMA 完成与 SPI 事务完成不是同一个概念

DMA 完成可能表示源数据已被搬进外设，而 SPI FIFO 或移位器仍在向屏幕输出。

因此，应分别判断：

- 什么时候 DMA 不再读取源内存。
- 什么时候可以改变 D/C 或 CS。
- 什么时候可以开始另一笔屏幕事务。
- 什么时候驱动应该报告本次操作完成。

源缓冲区可能先于总线释放，但驱动必须有明确约定。最初实现时，可以在已确认的事务完成条件后统一收尾，避免把不同事件混在一起。

任何等待都应有项目标准的超时和错误处理，不能让一次异常永久阻塞 GUI。

## 11. 异步传输最重要的是缓冲区所有权

一次异步调用返回，通常只说明请求已经提交，不说明像素传输已经完成。

因此，下面这个思路是错误的：

```text
启动 DMA
    -> 立即通知 GUI 刷新完成
    -> GUI 覆盖同一缓冲区
    -> DMA 还在读取被覆盖的数据
```

画面可能出现随机颜色、旧新数据混合或偶发局部异常。

### 11.1 一块缓冲区的正常状态

```text
FREE
  |
  v
DRAWING
  |
  v
READY
  |
  v
TRANSFERRING
  |
  v
确认所有相关消费者已释放
  |
  v
FREE
```

状态之间需要明确的拥有者和事件。

在 `TRANSFERRING` 状态中：

- 不覆盖源像素。
- 不释放源内存。
- 不改变仍被异步接口使用的描述符或参数。
- 不提交会破坏当前窗口的另一条命令。

如果命令参数采用异步发送，它们也必须具有足够长的生命周期，不能只保护像素数组而忽略栈上的窗口参数。

### 11.2 总线锁要覆盖完整的屏幕事务

如果多个任务或设备共享传输资源，应串行管理：

```text
设置窗口 -> 开始像素写入 -> 像素事务完成
```

不能设置好窗口就提前释放屏幕访问，让另一个任务改变窗口，然后继续发送原来的像素。

是否允许在像素分块之间插入其他设备事务，取决于屏幕协议、CS 规则和驱动设计；不要默认允许。

### 11.3 错误状态也需要完成生命周期

发生启动失败、超时或外设错误时：

1. 明确记录失败，停止提交新任务。
2. 按驱动接口中止当前操作。
3. 确认 DMA 和相关硬件不再访问源缓冲区。
4. 依据端口约定释放或重置资源。
5. 向上层报告失败，并按恢复策略重新初始化或重绘。

未经中止确认，不能把缓冲区重新标记为可用。

同样，也不能为了避免 GUI 卡住，就无条件宣告“显示成功”。

对 LVGL 而言，完成通知承担的是缓冲区交接职责，不是图像正确显示的证明。错误必须通过另外明确的错误通道保留下来。

## 12. 两块小缓冲区，怎样形成流水线？

以 320 像素宽、40 行、RGB565 为例：

```text
一块缓冲区：320 × 40 × 2 = 25,600 B = 25 KiB
两块缓冲区：50 KiB
```

可以采用这样的顺序：

```text
时间 ->

CPU：绘制 A | 绘制 B       | 等待 / 绘制 A | 绘制 B ...
SPI：       | 发送 A       | 发送 B        | 发送 A ...
```

前提是：

- SPI 传输确实在后台进行。
- CPU 绘制另一块内存时不破坏正在发送的缓冲区。
- 命令和像素提交保持正确顺序。
- 发送完成后，缓冲区才交回绘制方。
- 队列与任务唤醒没有把可重叠时间重新变成忙等。

这两块是局部绘制 / 发送缓冲区，不是两个完整显示帧。

它们主要改善处理吞吐和 CPU 可用时间，并不自动消除屏幕 GRAM 扫描中的撕裂。

### 12.1 缓冲区太小或太大，各有什么问题？

太小：

- 频繁设置窗口和启动传输。
- 更多固定软件开销。
- 更容易受到调度间隔影响。

太大：

- RAM 占用增加。
- 单次缓冲区释放时间变长。
- 绘制与传输阶段的配合未必更好。

应在多个块大小下测量端到端结果，不把“屏幕十分之一”或某个行数当成所有平台的最优值。

### 12.2 分块写入怎样保持正确？

对每块设置独立窗口，是一种容易验证的起点。

如果打算只设置一次整屏窗口，再连续发送多个块，需要确认控制器允许的续写方式和片选边界。

最后一块不足完整块高度时，应按真实高度和有效字节数发送，不把缓冲区剩余空间当作有效像素。

## 13. 局部刷新：只发送真正变化的区域

假设屏幕为 320 × 240、RGB565。

完整画面需要 153,600 B，而前面的 100 × 40 区域只需要 8,000 B。

像素数据量减少：

```text
153,600 / 8,000 = 19.2 倍
```

在假设的单线 40 MHz 链路上，不计命令和间隔：

| 更新范围 | 像素字节数 | 理想纯像素时间 |
| --- | --- | --- |
| 整屏 320 × 240 | 153,600 B | 30.72 ms |
| 区域 100 × 40 | 8,000 B | 1.60 ms |

如果该小区域每秒更新 60 次，纯像素量为：

```text
8,000 × 60 = 480,000 B/s = 0.48 MB/s
```

这说明局部界面与整屏动画，对同一条 SPI 链路的要求可以差很多。

但不能把 19.2 倍的数据量缩减直接写成“GUI FPS 提高 19.2 倍”。实际还存在绘制、固定开销、面板扫描和其他任务。

### 13.1 多个小区域，要不要合并？

分开传输会增加事务次数，合并成大矩形则可能增加像素量。

可以用一个简单模型判断：

```text
分开发送时间 ≈ sum(S_i) / B + n × T_setup
合并发送时间 ≈ S_bbox / B + T_setup
```

其中：

- `S_i`：每个区域的像素字节数。
- `S_bbox`：合并后的包围矩形像素字节数。
- `B`：有效像素吞吐。
- `T_setup`：每次事务的固定设置开销。

如果合并新增的传输时间小于节省的设置时间，合并才可能有收益。

不能把两个相距很远的小数值区域无条件合并成一个大矩形。

移动对象还需要重绘旧位置；阴影和抗锯齿也可能扩大区域。应观察框架实际产生的无效区域，而不是只看对象的名义尺寸。

## 14. TE 同步：有帮助，但不是无撕裂保证

带 GRAM 的屏幕自己扫描画面时，主控同时写入 GRAM，也可能出现新旧内容交错。

某些控制器通过 TE 信号报告特定扫描事件，主控可以据此安排写入。

但要确认：

- TE 的含义和输出模式。
- 面板扫描方向与像素写入方向。
- 更新区域在一次扫描中的位置。
- 可用写入时间和实际传输时长。
- 控制器是否提供其他缓冲或同步机制。

例如，320 × 240、RGB565、单线 40 MHz 的整屏纯像素传输已需 30.72 ms。

若面板扫描为 60 Hz，周期约为 16.67 ms。仅仅等到一个 TE 边沿再开始传输，并不能证明整个更新过程都处于安全的扫描窗口。

无撕裂需要结合具体扫描与写入时序分析，不能只看有没有接 TE 引脚。

## 15. QSPI：先匹配事务，再讨论四倍吞吐

QSPI 显示的吸引力很直观：像素数据阶段使用四条线，同频率下理论吞吐比单线更高。

但实际可行性来自协议匹配，不来自名称相同。

### 15.1 为屏幕列一张事务表

| 阶段 | 需要核对的条件 |
| --- | --- |
| 指令 | 操作码、长度、线宽 |
| 地址 / 控制字段 | 字段语义、长度、顺序和线宽 |
| 参数 | 字节数、线宽、是否与指令连续 |
| 转换 | 线宽切换、方向切换、等待周期 |
| 像素数据 | 格式、线宽、长度和顺序 |
| 结束 | CS、空闲间隔和事务完成定义 |

有些资料用三段式线宽表示法描述指令、地址和数据阶段，例如 `1-1-4`。应先确认目标屏幕文档是否采用同样的定义，不能把 SPI NOR 的字段含义直接套到显示协议中。

屏幕的“地址”也不一定是普通线性内存地址；它可能来自窗口命令、控制字段或特定封装协议。

### 15.2 主控需要具备哪些事务能力？

对 i.MX RT 上的候选外设，应核对：

- 能否生成每个阶段的线宽和位数。
- 是否允许所需的命令、等待及数据组合。
- 能否正确控制 CS 和阶段边界。
- 是否有适合像素传输的间接访问或其他接口。
- 是否存在 DMA、FIFO 和长度限制。
- SDK 是否已经提供该显示协议的适配。

某些平台的 FlexSPI 具有可配置事务能力，但是否能用于目标 QSPI 屏，仍要落实到具体控制器、协议和驱动。

不能把屏幕假装成普通 NOR Flash 后，就默认地址映射、读写操作和访问时序完全成立。

### 15.3 如果与 XIP 或资源 Flash 共享控制器

还需要考虑：

- 显示传输是否与程序取指或资源读取竞争。
- 活跃的 Flash 读序列是否会被修改。
- 控制器忙状态是否影响其他访问。
- 片选、引脚和时钟是否可独立配置。
- SDK 是否明确支持这种共享方式。

不要在运行中擅自修改正在被 XIP 使用的读序列或时钟，再期待显示传输和程序执行都不受影响。

应优先采用已有且明确支持的配置；否则把共享方案作为独立验证项。

### 15.4 一个纯吞吐算例

假设像素数据确实以四线、单边沿、40 MHz 发送：

```text
理论带宽 = 40,000,000 × 4 / 8 = 20 MB/s
320 × 240 RGB565 时间 = 153,600 / 20,000,000 = 7.68 ms
```

纯传输吞吐约为 130.21 次/s，但不代表面板或 GUI 能显示 130.21 张不同完整画面。

同样条件下，800 × 480 的纯像素时间仍需 38.4 ms。

四线提升带宽，但不会自动解决所有分辨率和刷新目标。

## 16. 接入 LVGL 时，需要对齐哪些语义？

后续 LVGL 移植篇会展开具体 API。本篇先明确显示端口需要完成的交接：

```text
LVGL 提供更新区域与像素
      |
      v
显示端口核对布局和格式
      |
      v
面板层设置目标窗口
      |
      v
传输层发送像素
      |
      v
按真实完成与错误状态收尾
      |
      v
缓冲区交回 LVGL
```

以 LVGL 9.2 的显示接口为例，`flush_cb` 接收待更新内容，`lv_display_flush_ready()` 承担刷新缓冲区交接的通知。

异步实现中，不能刚启动 DMA 就调用完成通知。

实际端口还应核对：

- 当前刷新模式是否提供紧凑局部数据。
- 源像素的实际 stride。
- 坐标旋转和 GRAM 偏移。
- 数据格式与字节顺序。
- 完成通知所需的线程与同步规则。
- 失败时的恢复和重新绘制策略。

一种容易管理的设计是由拥有显示状态机的任务处理收尾，中断只发送该端口允许的完成或错误通知。不要把普通 GUI 调用随意放到中断里。

## 17. 一套可以在板卡上执行的验证顺序

### 17.1 正确性测试

| 测试 | 应验证什么 |
| --- | --- |
| 黑、白、红、绿、蓝 | 格式、通道和字节顺序 |
| 色条与棋盘格 | 数据连续性与像素排列 |
| 四角标记 | 方向、偏移和坐标范围 |
| 100 × 40 窗口更新 | 端点、长度和区域映射 |
| 非整块高度的更新 | 尾块长度与边界 |
| 带 stride 的源区域 | 行间距处理 |
| 连续异步更新 | 缓冲区生命周期和事件顺序 |
| 模拟失败或超时 | 中止、资源释放与恢复 |

对异步测试，建议使用明显不同的连续图案，帮助暴露缓冲区被提前覆盖的问题。

### 17.2 性能记录

| 模式 | 范围 | 传输方式 | 记录状态 |
| --- | --- | --- | --- |
| 基线 | 整屏 | 阻塞 | 未测 |
| 对照 | 整屏 | DMA | 未测 |
| 局部 | 100 × 40 | DMA | 未测 |
| 分块 | 整屏、不同块高度 | 双缓冲 DMA | 未测 |
| QSPI〔条件满足时〕 | 相同范围 | 已验证的四线协议 | 未测 |

每项至少记录：

- 芯片、板卡、屏幕、SDK 和驱动版本。
- SCLK 实测值、像素格式和有效字节数。
- 命令 / 设置时间。
- 像素传输时间。
- 完整更新耗时。
- CPU 占用和缓冲区容量。
- 是否存在撕裂或传输错误。

用以下指标比较链路：

```text
有效像素吞吐 = 有效像素字节数 / 对应测量时间
```

说明测量时间是否包含窗口设置、等待和缓存维护；不同边界的结果不能直接比较。

如果使用 GPIO 或逻辑分析仪标记时间，分别观察 DMA 源读取结束和实际总线发送结束，避免只测到了提交调用。

## 18. 常见问题与排查顺序

| 现象 | 优先排查 |
| --- | --- |
| 背光亮但没有图像 | 电源、复位、初始化、D/C、CS、时钟与数据 |
| 红蓝互换 | RGB / BGR 配置与数据通道 |
| 颜色明显异常 | RGB565 字节顺序、帧宽、像素格式 |
| 图像偏移 | 模组可见区域、GRAM 偏移和方向 |
| 每行错位 | 窗口宽度、源 stride、发送字节数 |
| 阻塞正常，DMA 异常 | 地址可达、Cache、宽度、长度与生命周期 |
| 偶发新旧图案混合 | 源缓冲区提前覆盖、事务交错 |
| 小区域正常，整屏很慢 | 有效吞吐、数据量、块间间隔 |
| 接上 TE 仍然撕裂 | TE 语义、扫描 / 写入关系与更新时间 |
| QSPI 没有提高吞吐 | 数据阶段是否真正四线、协议开销、软件间隔 |

这些条目是建立假设的起点，不是根据现象直接判定根因。

先回到最小正确基线，再逐项加回 DMA、双缓冲、提速和 GUI，通常比同时调整很多参数更有效。

## 19. 小结：SPI 屏的关键，是少发、正确发、安全交接

对带 GRAM 的串行屏，可以把设计重点总结为：

1. **少发：** 尽可能只发送实际需要更新的像素。
2. **正确发：** 窗口、坐标、格式、字节序、stride 和数量一致。
3. **安全交接：** DMA、SPI 和 GUI 对缓冲区生命周期达成同一个约定。
4. **先匹配再提速：** QSPI 的收益建立在事务能力与屏幕协议兼容之上。

当这些条件都明确之后，DMA 和双缓冲才有可靠的性能价值。
