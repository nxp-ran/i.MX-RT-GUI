## 1. 为什么这笔账要在接线之前算？

一个常见开发过程是：先挑一块看起来合适的屏幕，再尝试连接芯片，最后才发现：

- 两个完整帧缓冲区放不下。
- SPI 每次整屏传输要花一百多毫秒。
- 开启透明效果后，外部存储带宽成为瓶颈。
- 像素时钟按有效分辨率配置，面板却无法正常同步。

这几类问题不一定要等到运行代码后才发现。

在[第 2 篇](02-platform-selection.md)的选型方法中，容量和吞吐是独立门槛。本篇就把这两个门槛展开。

先记住三个不同的量：

```text
容量：某一时刻要保存多少数据？
吞吐：每秒必须处理或传输多少数据？
时序：数据必须在什么时间窗口内到达？
```

容量够，不代表每秒搬得动；平均吞吐够，也不代表每个显示时段都能及时供数。

## 2. 第一张账单：像素格式

同样是一个像素，在不同环节可能占用不同数量的字节。

| 格式 | 颜色位数与含义 | 紧凑存储字节数 | Alpha |
| --- | --- | --- | --- |
| RGB565 | R 5 位、G 6 位、B 5 位 | 2 B/pixel | 无 |
| RGB888 | R、G、B 各 8 位 | 3 B/pixel | 无 |
| XRGB8888 | 32 位容器，含 24 位 RGB 与未用字段 | 4 B/pixel | 不作为有效 Alpha |
| ARGB8888 | 24 位 RGB 加 8 位 Alpha | 4 B/pixel | 有 |

这张表只描述常见格式的紧凑容量。

实际使用时，还要区分：

- 图片资源的编码格式。
- 解码后的像素格式。
- LVGL 绘制目标格式。
- PXP / GPU 接受的输入和输出格式。
- 显示帧缓冲区的存储格式。
- 屏幕链路上传输的格式。

例如，资源可能压缩存放在 Flash，解码后成为 ARGB8888 图片，再混合到 RGB565 帧缓冲区。

此时：

- Flash 容量按压缩文件算。
- 解码缓冲按 ARGB8888 算。
- 显示帧按 RGB565 算。
- 内存带宽要同时算读取和写入。

不能拿其中一个格式替代所有环节。

此外，RGB888 在某些硬件中未必允许以每像素 3 字节的方式作为目标缓冲；有些路径要求 32 位容器或特定对齐。必须根据实际配置核算。

## 3. 第二张账单：帧缓冲容量

### 3.1 最简单的完整帧计算

在紧凑存储、不考虑行填充的情况下：

```text
M_frame = W × H × b
```

其中：

- `W`：宽度，单位 pixel。
- `H`：高度，单位 pixel。
- `b`：每像素字节数，单位 B/pixel。

常见分辨率的容量量级如下：

| 分辨率 | RGB565 单帧 | RGB565 两帧 | ARGB8888 单帧 |
| --- | --- | --- | --- |
| 320 × 240 | 153,600 B = 150 KiB | 300 KiB | 300 KiB |
| 480 × 272 | 261,120 B = 255 KiB | 510 KiB | 510 KiB |
| 800 × 480 | 768,000 B = 750 KiB | 1,500 KiB | 1,500 KiB |
| 1024 × 600 | 1,228,800 B = 1,200 KiB | 2,400 KiB | 2,400 KiB |

ARGB8888 两帧的容量，还要在对应单帧基础上乘以二。

单位约定：

```text
1 KiB = 1,024 B
1 MiB = 1,048,576 B
1 MB  = 1,000,000 B
```

内存容量使用 KiB / MiB；本文带宽使用十进制 MB/s。不要在比较过程中混淆。

### 3.2 行跨度为什么会增加容量？

一行图像的实际占用空间，称为行跨度或 stride。

若每行要求按 `A` 字节对齐，常见预算方式是：

```text
row_bytes = W × b
stride = ceil(row_bytes / A) × A
M_frame = stride × H
```

假设一块图像缓冲区为 454 × 480，RGB565，每行按 64 字节对齐：

```text
紧凑行长度 = 454 × 2 = 908 B
实际行跨度 = ceil(908 / 64) × 64 = 960 B

紧凑容量 = 908 × 480 = 435,840 B
实际容量 = 960 × 480 = 460,800 B = 450 KiB
额外空间 = 24,960 B = 24.375 KiB
```

这只是演示行对齐影响的假设，不表示某一芯片统一要求 64 字节行对齐。

另外，基地址对齐与行跨度对齐不是一回事。缓冲区首地址对齐，不自动意味着每一行都符合目标硬件要求。

### 3.3 局部绘制缓冲区怎么算？

如果每次只绘制 `h` 行：

```text
M_draw = stride_draw × h
```

对于 800 像素宽、40 行、RGB565、紧凑存储：

```text
800 × 40 × 2 = 64,000 B = 62.5 KiB
```

两块这样的缓冲区需要 125 KiB。

但要结合显示架构理解它的收益：

- 带 GRAM 的屏幕，可以接收局部像素并保留整幅画面。
- 连续扫描方案即使采用小绘制缓冲区，通常仍需完整显示帧缓冲区。
- 如果绘制直接进入完整显示帧，就不能再把同一块内存重复计为独立绘制缓冲。

**预算时按实际分配的内存块计数，而不是按概念名称计数。**

## 4. 总内存不是“帧大小乘以二”

GUI 项目通常还有许多与帧缓冲不同的内存需求。

下面给出一份假设预算。为演示各项叠加，这里明确采用“两块完整显示帧 + 两块独立局部绘制缓冲区”，不是要求每个项目都使用该方案。

| 内存项目 | 假设配置 | 容量 |
| --- | --- | --- |
| 显示帧缓冲区 | 800 × 480，RGB565，两块 | 1,536,000 B = 1,500 KiB |
| 独立绘制缓冲区 | 800 × 40，RGB565，两块 | 128,000 B = 125 KiB |
| 临时离屏图层 | 200 × 100，ARGB8888，一块 | 80,000 B = 78.125 KiB |
| 解码工作区 | 假设预算 | 65,536 B = 64 KiB |
| 图片与字体运行缓存 | 假设预算 | 131,072 B = 128 KiB |
| 应用、GUI 堆与任务栈等 | 假设预算 | 262,144 B = 256 KiB |
| **合计** | 不含额外安全余量 | **2,202,752 B = 2,151.125 KiB** |

这个方案已经超过 2 MiB，即 2,097,152 B，超出 105,600 B。

如果只看“两个 RGB565 帧缓冲区需要约 1.465 MiB”，就会误以为 2 MiB 平台仍有充足余量。

实际项目还需根据以下情况调整：

- 图层和解码工作区是否同时存在。
- 哪些缓冲区可以安全复用。
- 某些资源是否已经包含在堆预算中，避免重复计数。
- 内存碎片、对齐和最坏场景是否增加占用。
- 哪些区域实际上不能交给显示或加速器使用。

安全余量应基于实际峰值、分配策略和可靠性要求，不是机械套一个统一百分比。

## 5. 第三张账单：显示扫描读取带宽

对于典型的完整帧连续扫描，先计算有效像素数据量：

```text
P_active = W × H × F_panel
B_scan = W × H × b_frame × F_panel
```

其中 `F_panel` 是面板扫描频率。

假设 800 × 480、RGB565、60 Hz：

```text
P_active = 800 × 480 × 60
         = 23,040,000 pixel/s

B_scan = 800 × 480 × 2 × 60
       = 46,080,000 B/s
       = 46.08 MB/s
```

这一项即使在静态画面下也可能持续存在，因为显示控制器仍要重复扫描已有帧。

如果帧缓冲采用 32 位格式：

```text
800 × 480 × 4 × 60 = 92.16 MB/s
```

这说明从 RGB565 切换为 32 位帧格式，不只增加容量，也增加有效扫描数据量。

上面的公式是有效像素读数量级，不是对实际总线事务的逐次计数。实际控制器可能采用突发访问、FIFO、不同存储布局或额外读取，应结合手册和测量。

## 6. 像素时钟，不能只用有效分辨率计算

在 RGB 连续输出中，像素时钟还覆盖同步和消隐时序。

常见计算关系为：

```text
H_total = H_active + H_sync + H_back_porch + H_front_porch
V_total = V_active + V_sync + V_back_porch + V_front_porch

PCLK = H_total × V_total × F_panel
```

下面使用一组**虚构的演示时序**，不能直接复制到某块面板配置中：

| 参数 | 示例值 |
| --- | --- |
| 水平有效像素 | 800 |
| 水平同步宽度 | 48 |
| 水平后肩 | 40 |
| 水平前肩 | 40 |
| 垂直有效行 | 480 |
| 垂直同步宽度 | 3 |
| 垂直后肩 | 29 |
| 垂直前肩 | 13 |
| 刷新率 | 60 Hz |

则：

```text
H_total = 800 + 48 + 40 + 40 = 928
V_total = 480 + 3 + 29 + 13 = 525

PCLK = 928 × 525 × 60
     = 29,232,000 Hz
     = 29.232 MHz
```

只按有效像素计算会得到 23.04 MHz，低于这组示例时序所需的像素时钟。

但也不要反过来把所有消隐像素时隙都算成有效帧缓冲读取：

- 像素时钟描述接口时序。
- 帧缓冲读取描述内存数据访问。
- 消隐区如何输出、如何预取，取决于具体控制器。

信号极性、数据采样边沿和控制器寄存器的计数编码，也需要分别核对，不能只把总数算对就认为配置完成。

## 7. 第四张账单：屏幕接口吞吐

### 7.1 单线 SPI 的理论上限

对单数据线、单边沿传输的 SPI：

```text
B_link_ideal = f_sclk / 8
```

假设像素写入的 SCLK 为 40 MHz：

```text
40,000,000 / 8 = 5,000,000 B/s = 5 MB/s
```

320 × 240、RGB565 完整一帧的纯像素传输时间：

```text
T_pixel = 153,600 / 5,000,000
        = 0.03072 s
        = 30.72 ms
```

对应理想整屏传输吞吐约为：

```text
1 / 0.03072 ≈ 32.55 次/s
```

这不是保证的可见 FPS。它还没有计入命令、间隔、绘制、缓存维护、面板扫描和调度。

如果目标改为 800 × 480：

```text
T_pixel = 768,000 / 5,000,000 = 153.6 ms
理想整屏传输吞吐 ≈ 6.51 次/s
```

这时，主频再高，也不能让同一条 40 MHz 单线链路完成 60 次/s 的整屏像素传输。

### 7.2 多数据线链路的量级

若像素数据阶段确实采用 `n` 条数据线、单边沿传输：

```text
B_link_ideal = f_sclk × n / 8
```

以同样的 40 MHz 和 RGB565 为例：

| 数据阶段 | 理论像素带宽 | 320 × 240 纯像素时间 | 800 × 480 纯像素时间 |
| --- | --- | --- | --- |
| 1 条数据线 | 5 MB/s | 30.72 ms | 153.6 ms |
| 4 条数据线 | 20 MB/s | 7.68 ms | 38.4 ms |

四线只是数据阶段的理想倍数。命令、地址或控制阶段可能仍使用不同线宽。

是否能够运行这种传输，必须由面板协议、主控事务能力和驱动实现共同确认。

不要把“主控支持 QuadSPI Flash”直接当作“主控支持这块 QSPI 显示屏”。

### 7.3 用效率系数做初步预算

可以用一个显式假设的效率系数 `eta` 估算：

```text
B_effective = B_link_ideal × eta
T_transfer = S_pixel / B_effective
```

例如，**仅假设**单线 40 MHz 的像素传输有效效率为 80%：

```text
B_effective = 5 × 0.8 = 4 MB/s

320 × 240：153,600 / 4,000,000 = 38.4 ms
800 × 480：768,000 / 4,000,000 = 192 ms
```

80% 不是某块板卡的测量结论，也不是所有 SPI 驱动的推荐参数。

后续应通过有效像素字节数和实测传输时间求出真实有效吞吐，再替换这个假设。

如果单独显式计算命令和间隔，就不要又用包含相同开销的效率系数重复扣减。

### 7.4 DSI 带宽也要区分有效负载与链路要求

以 800 × 480、60 Hz、链路有效像素使用 RGB888 为例：

```text
有效像素位率 = 800 × 480 × 60 × 24
             = 552.96 Mbit/s
```

若使用两个数据 Lane，平均分摊的有效负载量级为 276.48 Mbit/s/Lane。

这只是有效像素的平均负载计算，不是 DSI PHY 可以直接采用的配置值。

实际还要考虑包结构、视频模式、消隐处理、可用发送窗口、HS / LP 切换和面板限制。

即使内存帧格式为 RGB565，也不能据此把链路的实际像素格式自动改算成 16 bit。

## 8. 局部更新，为什么经常比加主频更有效？

假设 800 × 480 的屏幕每次只更新有效画面的 5%，RGB565：

```text
单次像素量 = 800 × 480 × 0.05 × 2
           = 38,400 B

若每秒更新 60 次：
像素传输量 = 38,400 × 60
           = 2.304 MB/s
```

相对于 46.08 MB/s 的每秒 60 次整屏像素量，这个变化非常明显。

但收益取决于系统架构。

### 8.1 带 GRAM 的按需传输方案

如果屏幕支持区域写入，局部更新可以直接降低主控到屏幕的传输量。

同时，主控通常也可以减少重绘像素。

### 8.2 完整帧连续扫描方案

局部绘制可以减少 CPU / 加速器的绘制访问。

但如果显示控制器仍然完整扫描 800 × 480、RGB565、60 Hz，扫描读取的 46.08 MB/s 基础量仍然存在。

因此：

> “LVGL 只重绘了 5%”不等于“显示控制器只读了 5%”。

另外，阴影、抗锯齿、移动对象的旧区域与新区域，都可能扩大真正的无效区域。预算要使用实际重绘和发送范围，而不是控件表面尺寸。

## 9. 内存带宽要把每个读写者加起来

有效显示数据量往往只是内存账单的一部分。

下面采用一个简化模型：

- 分辨率 800 × 480。
- 每秒完成 60 次完整画面处理。
- 显示帧使用 RGB565。
- 所列源和目标访问都经过同一个被统计的存储路径。
- 不计 Cache、突发、压缩、额外中间缓冲和硬件内部复用。

| 操作 | 每像素绘制侧访问 | 绘制侧带宽 | 加上显示扫描后的合计 |
| --- | --- | --- | --- |
| 纯色写入 RGB565 | 写 2 B | 46.08 MB/s | 92.16 MB/s |
| RGB565 图片复制 | 读 2 B + 写 2 B | 92.16 MB/s | 138.24 MB/s |
| ARGB8888 前景混合到 RGB565 背景 | 读 4 B + 读 2 B + 写 2 B | 184.32 MB/s | 230.40 MB/s |

第三种情况可以这样复算：

```text
绘制访问 = 800 × 480 × 60 × (4 + 2 + 2)
         = 184,320,000 B/s

显示读取 = 46,080,000 B/s
总量 = 230,400,000 B/s
```

这不是某一 PXP 或 GPU 的实测总线占用，也不是每种混合实现都必须产生完全相同的外部事务。

它的价值是说明：**透明混合的工作量不能只按最终画面的两个字节来算。**

如果资源读自另一条总线，应分别统计相关路径；如果又增加完整拷贝，则需额外加入该次读取和写入。

### 9.1 为什么双缓冲不会自动把扫描带宽翻倍？

增加一块完整帧缓冲区，首先增加的是容量。

典型双缓冲方案中，显示控制器每个扫描周期读取其中一块，并不因此同时扫描两块。

但后台绘制、旧内容同步和额外复制可能增加其他读写量。这些增加要按实际实现计数，不能仅因为“有两块帧”就把所有带宽乘以二。

### 9.2 为什么 GPU 更快，显示却可能没更快？

GPU 可能降低 CPU 计算时间，但它仍然需要读取资源、写出结果，并与显示扫描竞争存储带宽。

如果原来受内存或屏幕链路限制，换成更快的绘制执行单元不一定提高可见更新速度。

这正是后续性能分析要测量整条链路，而不只测量某个绘图函数的原因。

## 10. 平均带宽够，不代表供数一定稳定

外部存储器常见的理论峰值计算，例如：

```text
16 位、100 MHz、每周期一次数据传输：
理论峰值 = 2 B × 100,000,000 = 200 MB/s
```

这个数字不能直接拿来与 230.40 MB/s 或 46.08 MB/s 比较后宣布可行。

需要先确认具体存储器和控制器确实允许这一运行条件，再考虑：

- 存储刷新、命令和行切换。
- 读写方向切换。
- CPU、DMA、加速器和显示控制器之间的争用。
- 突发长度、访问连续性和仲裁。
- Cache 维护及其他业务负载。

显示控制器还可能要求在特定时间内填充 FIFO。平均每秒的数据量足够，某一行或某一次突发仍可能供数不及时。

建议至少观察：

1. 静态扫描时的基础占用。
2. 持续完整更新时的带宽压力。
3. 加入典型业务负载后的稳定性。
4. FIFO 欠载等异常是否出现。
5. 短时峰值，而不仅是长时间平均值。

## 11. 刷新吞吐与响应延迟分开预算

对串行执行的绘制与传输，可以初步写成：

```text
T_update = T_draw + T_transfer + T_sync
```

在允许重叠的双缓冲流水线中，理想稳态处理周期可能接近：

```text
T_cycle ≈ max(T_draw, T_transfer) + 不能重叠的开销
```

但这个周期不等于用户输入到可见变化的延迟。

输入延迟还可能包含：

- 采样等待。
- GUI 任务调度。
- 更新队列等待。
- 换帧或 TE 同步等待。
- 面板扫描到目标区域的时间。
- 面板自身响应。

吞吐优化和延迟优化不总是同一个方向。增加排队深度可能让执行单元更忙，却让新输入等待更久。

## 12. 用一段脚本复算预算

下面使用 Python 标准语法计算本篇的 800 × 480 算例，无需第三方依赖。

它不检测芯片能力，不访问硬件，只验证假设下的算术。修改输入前，应自行核对目标格式、时序和接口条件。

```python
width, height = 800, 480
bytes_per_pixel = 2
alignment = 64
frame_buffers = 2
panel_hz = 60

row_bytes = width * bytes_per_pixel
stride = ((row_bytes + alignment - 1) // alignment) * alignment
frame_bytes = stride * height
allocated_bytes = frame_bytes * frame_buffers
scan_bytes_per_second = width * height * bytes_per_pixel * panel_hz

h_total = width + 48 + 40 + 40
v_total = height + 3 + 29 + 13
pixel_clock = h_total * v_total * panel_hz

spi_clock = 40_000_000
data_lines = 1
assumed_efficiency = 0.8
link_bytes_per_second = spi_clock * data_lines * assumed_efficiency / 8
pixel_bytes = width * height * bytes_per_pixel
transfer_ms = pixel_bytes / link_bytes_per_second * 1000

print(f"Stride: {stride:,} B")
print(f"One frame: {frame_bytes:,} B ({frame_bytes / 1024:.3f} KiB)")
print(f"Frame allocation: {allocated_bytes:,} B")
print(f"Active scan payload: {scan_bytes_per_second / 1_000_000:.3f} MB/s")
print(f"Example RGB PCLK: {pixel_clock / 1_000_000:.3f} MHz")
print(f"Assumed SPI payload rate: {link_bytes_per_second / 1_000_000:.3f} MB/s")
print(f"Estimated full-screen SPI transfer: {transfer_ms:.3f} ms")
```

对应输出：

```text
Stride: 1,600 B
One frame: 768,000 B (750.000 KiB)
Frame allocation: 1,536,000 B
Active scan payload: 46.080 MB/s
Example RGB PCLK: 29.232 MHz
Assumed SPI payload rate: 4.000 MB/s
Estimated full-screen SPI transfer: 192.000 ms
```

脚本中的 RGB 时序与 SPI 链路是两种独立方案的预算演示，不表示同一屏幕同时以这两种接口运行。

## 13. 把预算结果变成一张检查表

| 项目 | 计算输入 | 验证方式 |
| --- | --- | --- |
| 帧容量 | 分辨率、实际格式、stride、数量 | 链接布局与实际分配 |
| 工作内存 | 局部缓冲、图层、解码、堆和栈 | 最坏场景峰值 |
| 扫描带宽 | 帧格式、面板扫描频率 | 控制器状态与实际存储访问 |
| 绘制带宽 | 资源读取、背景读取、目标写入 | 操作计时与访问路径 |
| 接口吞吐 | 数据线宽、时钟、协议、更新面积 | 有效像素量 / 实测时间 |
| 显示时序 | 同步、前后肩、极性、像素时钟 | 面板资料与波形 |
| 同步开销 | DMA 完成、换帧、TE、Cache | 时间线和异常记录 |
| 响应延迟 | 输入、调度、排队、扫描 | 输入事件到可见变化 |

预算时应保留“理论值”“假设值”“实测值”三个不同栏位。

只有完成实际测量之后，才把假设替换为验证结果。

## 14. 小结：一张画面，背后有四张账单

在接线和写驱动之前，应至少算清：

1. **容量账：** 哪些像素和工作区需要同时保存？
2. **时序账：** 面板要求什么时候输出数据？
3. **接口账：** 主控到屏幕每秒能传多少有效像素？
4. **内存账：** 绘制、复制、混合和扫描一共读写多少数据？

局部更新减少的是实际变化引起的工作量；硬件加速改变的是任务执行方式。两者都不能自动消除完整扫描的基础带宽，也不能替代正确的容量与协议预算。
