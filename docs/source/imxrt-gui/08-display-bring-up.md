# 第 8 篇：一套可复用的屏幕点亮与排障流程

> 系列：[从点亮屏幕到高性能 GUI：i.MX RT 图形系统实战](README.md)
>
> 上一篇：[MIPI DSI 屏——高速串行显示链路](07-mipi-dsi-display.md)
>
> 下一篇：[LCDIF / eLCDIF 等显示控制器如何工作？](09-lcdif-elcdif.md)
>
> 本篇目标：建立从硬件到 GUI 的验证顺序，让黑屏、偏色、错位、花屏和撕裂都能沿数据路径定位。
>
> 验证边界：本文提供检查清单、测试图案和示意故障推演，没有声称某块实际板卡已经通过测试。时序与电气要求仍应以芯片、开发板和面板资料为准。

## 1. 排障的第一步，不是修改初始化数组

屏幕不显示时，很容易立即替换初始化代码、调整像素时钟，或者关闭 Cache。

这些方法有时会改变现象，却不一定找到根因。多个参数同时修改，还可能丢掉原本有价值的证据。

先把“黑屏”说得更精确：

- 背光是否亮？
- 是完全没有有效像素，还是显示全黑图像？
- 上电首次失败，复位后正常，还是偶发失败？
- 固定图案正常，加入动画才异常？
- CPU、传输外设和面板端各自处于什么状态？

现象越具体，下一步越有依据。

## 2. 每次实验先固定条件

建立一张最小实验记录：

| 分类 | 至少记录 |
| --- | --- |
| 硬件 | 芯片完整型号、板卡版本、模组与控制器 |
| 连接 | 接口模式、连接器、电源、复位、背光、触摸 |
| 软件 | SDK、驱动、编译器、优化选项 |
| 时钟 | CPU、存储、接口及显示时钟的实际值 |
| 像素 | 分辨率、格式、stride、字节序、方向和偏移 |
| 内存 | 缓冲地址、容量、可达性、对齐、Cache/MPU 属性 |
| 刷新 | 单/双缓冲、区域范围、传输方式、完成事件 |
| 复现 | 场景、操作顺序、成功与失败次数 |

成功和失败都保留条件，才能判断哪些差异真正影响结果。

日志中不需要保存认证信息或无关敏感数据；记录与显示故障直接有关的配置和状态即可。

## 3. 七道检查门，逐层通过

```text
1. 资料与连接
       |
       v
2. 电源、复位与背光
       |
       v
3. 外设、时钟与接口状态
       |
       v
4. 面板初始化或扫描时序
       |
       v
5. 像素内容与内存路径
       |
       v
6. 传输完成与缓冲区同步
       |
       v
7. GUI、输入与综合负载
```

顺序用于减少未知量，不是所有芯片固定的寄存器启动顺序。

某一层未验证时，应明确标记，不把“示例下载成功”视为所有层都通过。

## 4. 先确认资料、供电和连接

### 4.1 资料与连接

核对模组接口，不只核对控制器名称。

同一个控制器可能支持多种接口，模组已经通过绑定位选定其中一种；同名连接器也可能有不同引脚排列。

检查信号电平、引脚复用和开发板跳线，避免把软件问题与连接问题混在一起。

### 4.2 电源与复位

检查：

- 模组和逻辑电源是否在允许范围。
- 上电顺序和稳定等待。
- 复位有效极性、保持时间和释放时刻。
- 背光驱动是否独立于显示控制器。

背光亮只能证明背光相关路径工作；不能证明屏幕控制器初始化完成。

连接、断开模组和测量应遵循板卡及面板操作要求，不以临时短接或超规格操作代替验证。

## 5. 按接口抓取不同证据

| 接口 | 最先观察 | 下一步验证 |
| --- | --- | --- |
| SPI / QSPI | CS、时钟、命令/数据与线宽 | 窗口、字节序、数据量和事务边界 |
| 8080 式并口 | CS、RS、WR/RD、数据总线 | 建立保持、周期、位宽与尾部传输 |
| RGB | PCLK、DE、HSYNC、VSYNC | 完整时序、有效数据、内存读取 |
| MIPI DSI | 电源/复位、Host/PHY 状态与命令结果 | 视频路由、格式、包与 HS 链路 |

这些方法对应前面几篇的具体接口流程：

- [SPI / QSPI](04-spi-qspi-display.md)
- [8080 / DBI](05-flexio-dbi-display.md)
- [RGB](06-rgb-display.md)
- [MIPI DSI](07-mipi-dsi-display.md)

普通逻辑分析仪适合部分低速数字事务，不应被当作所有高速差分问题的诊断工具。

读取面板寄存器也需要对应接口、命令和返回路径支持。一次读取失败不是判定屏幕损坏的充分证据。

## 6. 图案要针对问题，而不是只显示一张照片

| 图案 | 容易暴露的问题 | 使用提醒 |
| --- | --- | --- |
| 黑白 | 基础显示与大面积更新 | 对字节交换和通道问题不敏感 |
| 红绿蓝 | 通道、格式、位映射 | 各颜色单独验证 |
| 不同强度色条 | 色阶与数据位 | 与目标位宽一致 |
| 四角不同标记 | 方向、偏移、有效区域 | 不使用对称标记掩盖镜像 |
| 行号或行颜色 | stride 与扫描布局 | 保证源图案本身正确 |
| 棋盘格 | 数据连续性与像素排列 | 改变格子大小比较 |
| 移动边界 | 撕裂和同步 | 静态正确后再使用 |
| 帧编号或明显交替颜色 | 新帧是否真正提交 | 与软件序号及事件记录对应 |

使用不同帧内容，能区分“没有更新”和“更新了但颜色一样”。

如果图案由 CPU 生成，先确认内存内容；如果由硬件测试发生器输出，说明它绕过了哪些环节。

## 7. 三个层级的最小软件基线

### 7.1 基线 A：不用 GUI

固定一帧或一个区域，生成纯色、色条和位置标记，验证基本显示。

这能排除布局、控件、资源解码和事件调度的影响。

### 7.2 基线 B：不用复杂流水线

在可行的接口上先用容易观察的同步流程；连续扫描方案先固定完整帧，不动态改写。

通过之后再引入 DMA、换帧和异步通知。

### 7.3 基线 C：最小 GUI

加入少量控件，先不使用复杂透明效果和大型资源。

随后依次加入输入、资源、动画、硬件加速和业务负载。

基线是隔离变量的方法，不表示最终产品必须放弃 Cache、DMA 或加速器。

## 8. 把状态和时间线一起记录

一次更新至少可记录：

```text
更新序号
  -> 绘制开始/完成
  -> 提交区域或帧地址
  -> DMA/处理完成
  -> 显示事件或实际换帧状态
  -> 缓冲区释放
```

对于连续扫描，DMA 完成、进入消隐、VSYNC 和新地址生效不一定是同一个事件。

日志应按事件真实语义命名，不把所有中断都叫“刷新完成”。

| 证据 | 用途 |
| --- | --- |
| 请求序号与缓冲地址 | 判断新旧内容与拥有者 |
| 中断状态快照 | 区分正常事件与异常 |
| 超时阶段与持续时间 | 判断卡在哪一层 |
| 欠载/总线/协议错误计数 | 判断负载相关问题 |
| GPIO 时间标记 | 观察提交与实际接口动作 |

先保存状态，再按 SDK 语义清除。清错误位只是确认收到事件，不代表故障已经修复。

中断中避免大量打印影响时序；使用目标平台允许的通知或轻量记录，在任务上下文处理。

## 9. 三个示意故障推演

以下是验证思路，不是已完成的板卡维修案例。

### 9.1 背光亮，屏幕全黑

假设是 RGB 方案。

1. 确认供电与复位。
2. 检查 PCLK 与同步是否存在。
3. 检查 DE 是否形成正确有效区域。
4. 检查控制器是否读取有效帧地址。
5. 检查内存图案是不是本来就全黑。
6. 检查信号映射与面板控制状态。

如果在第 2 步发现没有 PCLK，就先定位时钟和模块状态，不急着修改字体或 LVGL 配置。

### 9.2 阻塞发送正常，DMA 偶发错图

1. 用同一图案、同一窗口对照。
2. 检查 DMA 地址可达与访问宽度。
3. 检查 CPU 写入是否对 DMA 可见。
4. 检查源缓冲与参数是否在传输期间被修改。
5. 检查末尾外设输出与完成通知。

改变 Cache 属性只应作为受控对照。若定位到维护缺失，应修正交接，而不是把所有内存永久改成不可缓存。

### 9.3 静态正常，加入动画和网络任务后花屏

1. 分开运行动画与业务负载。
2. 记录显示 FIFO 或总线异常。
3. 检查共享存储流量与最长访问延迟。
4. 检查任务调度和换帧等待。
5. 每次只修改直接相关的一项配置并复测。

如果某次修改让花屏暂时消失，还需要在相同条件下重复验证，不能直接当作根因确认。

## 10. 错误处理也是显示驱动的一部分

推荐错误收尾原则：

- 不在失败后继续发送成功状态。
- 不在未确认中止时释放正在被读取的内存。
- 不无条件把故障帧当作完成帧。
- 记录失败阶段、请求范围和有效状态。
- 按项目策略恢复外设、重新初始化或重绘。
- 为必要等待提供超时与可解释的失败路径。

画面不更新而 GUI 不报错，会让定位成本比一次明确失败更高。

恢复之后，还要证明资源拥有者、队列和缓冲状态回到一致状态，而不是只让显示重新亮起来。

## 11. Bring-up 完成的验收条件

| 层级 | 建议验收 |
| --- | --- |
| 连接与电气 | 与资料一致，复位和时钟可解释 |
| 固定图案 | 颜色、方向、尺寸与区域正确 |
| 动态更新 | 新内容生效，缓冲交接可靠 |
| 异常与恢复 | 超时或中止能明确处理 |
| 负载 | 典型业务场景下无未解释错误 |
| 重复性 | 冷启动、复位、连续更新可重复 |
| 记录 | 平台、配置、证据与已知限制齐全 |

重复次数、持续时间和性能阈值应根据项目需求预先确定。本篇不以任意一次成功或任意固定运行时长宣告所有产品合格。

把“未测”保留下来，比把未知项写成“通过”更有工程价值。

## 12. 小结

屏幕排障的核心是：

1. 固定条件，明确现象。
2. 从硬件和接口向像素及 GUI 逐层检查。
3. 用合适图案和时间线建立证据。
4. 每次修改一个相关变量，重复验证。
5. 把错误与恢复也纳入验收。
