# 第 6 篇：RGB 屏——理解像素时钟与连续扫描

> 系列：[从点亮屏幕到高性能 GUI：i.MX RT 图形系统实战](README.md)
>
> 上一篇：[8080 / DBI 并口屏——利用 FlexIO 等资源实现显示](05-flexio-dbi-display.md)
>
> 下一篇：[MIPI DSI 屏——高速串行显示链路](07-mipi-dsi-display.md)
>
> 本篇目标：把面板时序转成显示控制器配置，并理解像素格式、帧缓冲、持续扫描和供数不足之间的关系。
>
> 适用范围：以主控显示控制器驱动 RGB 面板为模型，不假设所有屏幕都有或都没有 GRAM。时序与预算是演示假设，不是某一模组的推荐参数或实测。

## 1. RGB 屏不是“更宽的 8080 总线”

两种接口都可能使用多根数据线，但工作方式不同。

在[第 5 篇](05-flexio-dbi-display.md)中，主控按窗口写入屏幕端存储；在本篇的 RGB 方案中，显示控制器按固定时序持续送出像素。

```text
CPU / 绘制单元
      |
      v
主控可访问的完整帧缓冲区
      |
      v
显示控制器：读取、排队、生成时序
      |
      v
RGB 数据 + PCLK + 同步信号
      |
      v
面板
```

画面不变时，GUI 可以不重绘，但显示扫描通常仍在继续。没有绘制任务不代表没有内存读取。

主控不必每个像素周期执行一次软件操作；持续供数由显示控制器负责。CPU 的任务是生成内容、管理缓冲区和处理同步。

## 2. 五类信号，构成一幅有时间关系的画面

| 信号 | 含义 | 需要确认 |
| --- | --- | --- |
| RGB 数据 | 当前像素的颜色分量 | 位映射、格式和有效电平 |
| PCLK | 像素时钟 | 频率、采样边沿和波形 |
| HSYNC | 水平同步 | 极性和脉宽 |
| VSYNC | 垂直同步 | 极性和脉宽 |
| DE | 有效像素指示 | 有效极性、位置和宽度 |

有的面板使用 DE 模式，有的依赖同步模式，有的组合使用。连接和控制器配置必须匹配模组要求。

“输出数据的边沿”与“面板采样的边沿”也要区分。配置宏中的 drive/capture 命名，必须结合实际驱动和面板资料理解。

不要根据“常见 RGB 屏”的经验统一设定极性和边沿。

## 3. 一行像素和一帧图像怎样排列？

以一种时序描述顺序为例：

```text
一行：
[HSYNC] [水平后肩] [有效像素] [水平前肩]
                    <--- DE 有效 --->

一帧：
[VSYNC] [垂直后肩] [有效显示行] [垂直前肩]
```

前肩、后肩和同步宽度不是无用参数，而是面板扫描时序的一部分。

常见关系为：

```text
H_total = H_active + H_sync + H_back_porch + H_front_porch
V_total = V_active + V_sync + V_back_porch + V_front_porch

PCLK = H_total × V_total × Refresh
```

水平时间通常用像素时钟周期表示，垂直时间通常用行表示。实际寄存器可能使用不同编码，不能把时间、计数和寄存器值混为一谈。

某些参数填写实际数量，某些寄存器需要数量减一。使用 SDK 配置结构时，应确认驱动已经完成哪些转换。

## 4. 从面板表格到配置表格

下面延续[第 3 篇](03-memory-and-bandwidth.md)的一组虚构时序：

| 面板参数 | 演示值 | 配置含义 |
| --- | --- | --- |
| 有效宽度 | 800 | 每行有效像素 |
| 有效高度 | 480 | 每帧有效行 |
| HSW / HBP / HFP | 48 / 40 / 40 | 水平同步、后肩、前肩 |
| VSW / VBP / VFP | 3 / 29 / 13 | 垂直同步、后肩、前肩 |
| 刷新率 | 60 Hz | 目标扫描节奏 |
| 极性与边沿 | 未指定 | 必须从实际面板资料补齐 |

计算：

```text
H_total = 928
V_total = 525
PCLK = 928 × 525 × 60 = 29.232 MHz

行周期 = 928 / 29,232,000 ≈ 31.746 us
帧周期 = 1 / 60 ≈ 16.667 ms
```

如果只能得到 30 MHz 的实际像素时钟，保持其他数量不变：

```text
实际刷新率 = 30,000,000 / (928 × 525) ≈ 61.576 Hz
```

不能因为在软件里写了“60 Hz”，就认为面板实际工作在 60 Hz。应检查时钟树和输出波形，并确认实际值仍在面板允许范围内。

## 5. 内存像素格式和 RGB 引脚宽度是两层配置

RGB565 的帧缓冲区每像素占 2 字节，并不意味着最终面板只有 16 根颜色数据线。

某些受支持的路径可以从内存 RGB565 生成更宽的输出；如何扩展位、如何映射颜色，取决于控制器配置。

同样，24 位 RGB 输出并不证明内存是紧凑的 RGB888：

| 环节 | 一个可能的选择 |
| --- | --- |
| 图片资源 | ARGB8888 |
| 绘制目标 | RGB565 |
| 帧缓冲存储 | RGB565，每像素 2 B |
| 输出总线 | 目标控制器支持的 RGB 位宽 |

本次核对的 eLCDIF RGB 示例采用 XRGB8888 内存帧，并独立配置输出总线。这正好说明二者必须分别检查。

### 5.1 引脚映射怎么验证？

建议先显示红、绿、蓝，再显示每个颜色分量的不同强度。

需要区分：

- 红蓝通道整体交换。
- 某一数据位未连接或映射错误。
- 低位未使用导致色阶变化。
- 内存格式与控制器解释不同。

SPI 发送中的字节交换方案不能不加分析地移植到 RGB 帧缓冲区。RGB 控制器直接解释内存，不是把所有内存字节原样串行发给屏幕。

## 6. 帧缓冲地址与行跨度

对于普通逐行排列的 RGB565 图像：

```text
pixel_address(x, y) = base + y × stride + x × 2
```

如果绘制方按 `stride = 1,664 B` 写入，而显示方每行按 `1,600 B` 读取，第一行可能正常，后续行会逐步错位。

基地址、有效宽度、行跨度和像素格式必须由同一份布局描述约束。

但这里有一个重要限制：

> 通用软件模型中存在 stride，不代表每种显示控制器的每个模式都能配置任意 stride。

本次核对的 eLCDIF RGB 配置结构没有独立的 stride 参数；LCDIFv2 的层缓冲配置则提供 `strideBytes`。要按目标路径安排内存，不要对没有该能力的接口想当然。

缓冲区还应满足地址对齐、内存可达和 Cache 一致性要求。不能仅因为 CPU 可以读写某段 RAM，就让显示控制器直接读取它。

## 7. 为什么必须持续供数？

显示控制器通常通过内部读取路径和 FIFO 把存储访问与像素输出节奏解耦。

```text
RAM / 总线 -> 控制器读取 -> FIFO -> 按 PCLK 输出
```

FIFO 能吸收短暂延迟，但容量有限。

若其他主设备长时间占用内存，FIFO 来不及补充，就可能出现欠载。具体显示结果与错误标志取决于控制器。

800 × 480、RGB565、60 Hz 的有效扫描读取量为：

```text
800 × 480 × 2 × 60 = 46.08 MB/s
```

这还没有计入绘制和资源读取。

如果 CPU 每秒完整写入 60 帧，简化模型中再增加 46.08 MB/s；透明混合和复制还会进一步增加流量。

**静态扫描、动态绘制和外部业务负载应分别测量，再合并验证。**

不要只看外部 RAM 的理论峰值，忽略实际仲裁和短时延迟。

## 8. 点亮 RGB 屏的最小初始化思路

一条容易验证的基线是：

1. 固定面板型号、引脚和供电方案。
2. 配置系统时钟、存储和显示模块时钟。
3. 在可达且满足对齐的 RAM 中准备完整帧。
4. 填入纯色或色条，完成必要的内存可见性处理。
5. 配置有效尺寸、前后肩、同步、格式和总线。
6. 设置有效帧地址，清理并启用需要的状态事件。
7. 按目标硬件顺序启动扫描、面板及背光。
8. 检查波形、实际频率和异常计数。

面板是否还需要额外初始化控制接口，以及背光何时开启，应以模组要求为准。这里不是所有板卡的统一启动顺序。

默认 SDK 参数只能作为结构示例，不能代替面板时序表。

## 9. 用脚本检查时序和扫描预算

下面脚本只计算假设值，不配置寄存器，也不检测实际时钟：

```python
width, height = 800, 480
hsw, hbp, hfp = 48, 40, 40
vsw, vbp, vfp = 3, 29, 13
refresh = 60
bytes_per_pixel = 2

h_total = width + hsw + hbp + hfp
v_total = height + vsw + vbp + vfp
pixel_clock = h_total * v_total * refresh
actual_clock = 30_000_000
frame_bytes = width * height * bytes_per_pixel

print(f"Totals: {h_total} pixels/line, {v_total} lines/frame")
print(f"Target PCLK: {pixel_clock / 1_000_000:.3f} MHz")
print(f"Line period: {h_total / pixel_clock * 1_000_000:.3f} us")
print(f"Frame period: {1000 / refresh:.3f} ms")
print(f"At 30 MHz: {actual_clock / (h_total * v_total):.3f} Hz")
print(f"RGB565 frame: {frame_bytes:,} B")
print(f"Active scan reads: {frame_bytes * refresh / 1_000_000:.2f} MB/s")
```

输出：

```text
Totals: 928 pixels/line, 525 lines/frame
Target PCLK: 29.232 MHz
Line period: 31.746 us
Frame period: 16.667 ms
At 30 MHz: 61.576 Hz
RGB565 frame: 768,000 B
Active scan reads: 46.08 MB/s
```

现场测量时，将真实 PCLK 代入，再核对行周期和帧周期，而不只判断“画面看起来正常”。

## 10. 从静态图案到动态更新

先固定一个完整帧，验证稳定扫描；然后再改变内容。

| 图案 | 主要验证 |
| --- | --- |
| 黑白与红绿蓝 | 基础显示、通道和像素格式 |
| 彩色色条 | 位映射与色阶 |
| 四角不同标记 | 显示方向、有效区域和偏移 |
| 行号或棋盘格 | 行跨度与扫描顺序 |
| 移动矩形 | 写入与扫描冲突 |
| 双帧交替颜色 | 提交、换帧与旧缓冲释放 |

在单帧方案中，CPU 修改正在扫描的内存，可能出现撕裂。双帧方案需要在正确事件后确认切换，不能只把地址写入寄存器就立刻修改旧帧。

局部更新能降低绘制成本，但连续扫描仍然读取显示所需的完整数据。

后续缓冲章节会专门讨论同步策略；本篇先建立“谁读取、何时读取”的认识。

## 11. 按现象分层排查

| 现象 | 初始检查方向 |
| --- | --- |
| 背光亮，但整屏无有效图像 | 电源、复位、控制器运行、PCLK、DE 与有效地址 |
| 图像整体偏移 | 前后肩、同步宽度、有效区域配置 |
| 红蓝互换 | 通道顺序、IOMUX、输出映射 |
| 色阶异常或某颜色位不变化 | 数据位连接、位映射、格式 |
| 每行逐步错位 | 布局、stride、宽度与读取模式 |
| 静态正常，动态花屏 | Cache、撕裂、带宽与缓冲区生命周期 |
| 加入其他任务后异常 | 仲裁、FIFO 欠载与访问延迟 |
| Debug 与 Release 表现不同 | 绘制时间、竞态、CPU 负载，不只看主频 |

欠载标志、总线错误和当前帧事件是重要证据。读取并记录状态，再用 SDK 正确清除；不能通过清标志把异常当作解决。

## 12. 小结

RGB 方案的本质，是显示控制器从主控帧缓冲区持续读取，并按面板要求输出时间连续的像素。

- PCLK 要根据完整时序计算。
- 输出总线格式与内存格式分开配置。
- 缓冲区布局必须匹配控制器真正支持的读取模式。
- 静态界面也可能持续占用扫描带宽。
- 动态更新还需要缓存、同步和所有权管理。
