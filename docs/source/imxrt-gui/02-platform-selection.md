## 1. 选 GUI 平台，为什么不能只比较主频？

在[第 1 篇](01-gui-system-overview.md)中，我们已经把 GUI 拆成了应用、绘制、存储和显示输出几个层次。

接下来，很多人会问：既然 GUI 要处理大量像素，是不是直接选主频最高的 i.MX RT 就可以了？

主频当然重要，但它不能回答下面这些问题：

- 目标芯片能不能连接这块屏幕？
- 完整帧缓冲区放在哪里，显示控制器能不能访问？
- 半透明图片、旋转和缩放由谁执行？
- SDK 有没有能够复用的驱动？
- 所选 LVGL 版本能不能使用芯片的加速器？
- GUI 运行时，还剩下多少 CPU 和内存给控制、通信及其他任务？

如果输出链路每秒只能传输几张完整画面，再快的 CPU 也不能让同一条链路传输几十张。

如果项目需要两个完整帧缓冲区，而可用内存只够一个，提高主频也不能补上容量差额。

因此，GUI 平台选型的顺序应该是：

```text
产品体验要求
    |
    v
屏幕与更新方式
    |
    v
容量、带宽和绘制工作量
    |
    v
芯片、封装、存储与开发板
    |
    v
SDK、驱动和 GUI 框架适配
```

不是先确定芯片，再寄希望于后续优化解决所有问题。

## 2. 把“我要一个 GUI”写成可检查的需求

“流畅”“好看”“支持中文”都不够具体。

选择硬件之前，建议至少整理以下需求。

| 维度 | 需要说明什么 | 为什么影响选型 |
| --- | --- | --- |
| 屏幕 | 分辨率、接口、控制器、显示方向 | 决定输出链路和基本数据量 |
| 更新 | 局部数值、滚动列表、整屏动画等 | 决定实际重绘和传输面积 |
| 体验 | 更新频率、输入延迟、撕裂要求 | 决定吞吐与同步策略 |
| 图形 | 透明混合、缩放、旋转、矢量图形 | 决定软件绘制和加速需求 |
| 资源 | 图片、中文字体、资源更新方式 | 决定 Flash、RAM 和加载开销 |
| 业务 | 控制周期、通信负载、实时性 | 决定 GUI 能占用多少系统资源 |
| 工程 | 封装、PCB、功耗、成本和供货 | 决定方案能不能落地 |
| 软件 | SDK、LVGL、RTOS、编译器版本 | 决定适配工作量和维护成本 |

例如，下面两个界面虽然都采用 320 × 240 屏幕，硬件需求却不相同：

**界面 A：温度控制面板**

- 数值和状态图标按需更新。
- 页面大部分区域静止。
- 不需要连续整屏动画。
- 希望为控制和通信任务保留较多 CPU 时间。

**界面 B：图片浏览与动态转场**

- 频繁改变大面积像素。
- 需要图片解码、缩放和透明混合。
- 更关注整帧吞吐、资源加载和峰值内存。

分辨率相同，不代表绘制工作量、资源占用和带宽需求相同。

## 3. “支持”必须分成四层

选型资料中最危险的词，是没有限定条件的“支持”。

### 3.1 第一层：芯片具有硬件能力

需要确认具体订货型号是否具有：

- 目标显示控制器或可用传输外设。
- 所需的 PXP、GPU 或其他图形能力。
- 足够的片上内存和外部存储接口。
- 相关模块之间可行的数据访问路径。

这里的确认对象应是具体型号，而不是只写“RT10xx”或“RT11xx”。

产品系列中的不同成员，可能在外设、内存、封装或工作频率上存在差异。

### 3.2 第二层：封装与开发板提供连接条件

芯片内部具有接口，不代表你手上的封装或开发板已经把它引出来。

还需要核对：

- 所选封装有没有足够的相关引脚。
- 引脚复用是否与 Flash、存储或其他业务外设冲突。
- 开发板上的接口电压、连接器和管脚排列是否匹配。
- 面板供电、复位、背光和触摸连接如何实现。
- 高速接口所需的 PCB 和信号完整性条件是否满足。

两块同样标注“支持 RGB 屏”的板子，连接器也未必兼容。

### 3.3 第三层：SDK 提供可用驱动

需要进一步确认：

- SDK 是否支持该芯片和该板卡版本。
- 是否提供控制器驱动及目标屏幕组件。
- 是否具备 DMA、异步完成通知和错误处理。
- 示例是否使用相同的屏幕、存储和时钟条件。
- 驱动适配是否涉及板级初始化或额外中间层。

“有一个显示示例”不等于“所有屏幕都能直接接入”。

### 3.4 第四层：LVGL 能使用这条路径

最后还要确认 GUI 层：

- 显示端口使用哪种刷新模式和缓冲方案。
- 所选 LVGL 版本是否提供目标加速后端。
- SDK 中的后端是否与这个 LVGL 版本兼容。
- 目标像素格式和任务类型是否走硬件路径。
- 不支持的任务如何软件回退。
- 线程、Cache 和异步生命周期是否正确处理。

可以把这四层写成一张项目状态表：

| 项目 | 芯片 | 板级 | SDK | LVGL |
| --- | --- | --- | --- | --- |
| 目标屏幕输出 | 待核对 | 待核对 | 待核对 | 待核对 |
| PXP 加速 | 待核对 | 存储与时钟条件待核对 | 待核对 | 待核对 |
| GPU 加速 | 待核对 | 存储与时钟条件待核对 | 待核对 | 待核对 |
| 外部帧缓冲 | 访问路径待核对 | 存储器与布线待核对 | 初始化待核对 | 布局待核对 |

每一个“已支持”都应附带依据。未完成的格子保留“待核对”，而不是默认绿色。

下面分两张表整理基本资源与图形路径。

表格用于展示选型方法，不替代目标芯片的数据手册、参考手册、勘误和完整订货型号信息。

**片上 RAM 总量不是“可直接分配给 GUI 的连续 RAM”。**

其中可能包含 TCM、普通片上 RAM、其他内核使用的区域，以及已经被程序、堆、栈或共享数据占用的空间。

### 4.3 一个值得记住的系列内差异

[RT1040 产品页](https://www.nxp.com/products/i.MX-RT1040)特别提到了 RT1043 的 LCD 支持，也介绍了系列中的其他成员。

这个例子提醒我们：系列级宣传页面可能汇集多个成员的能力。不能从页面里看到一个 LCD 条目，就推断每个 RT104x、每种封装都具有完全相同的显示配置。

本文没有把未逐项核对的 RT104x 成员塞进统一矩阵。其他四位数型号也应按同样方法补充，而不是根据数字位置推测。

## 5. 三类不同的 GUI 平台思路

比起把型号简单排成性能高低，更有价值的做法，是按系统架构分类。

### 5.1 以软件绘制和屏幕 GRAM 为中心

典型数据路径：

```text
LVGL / 应用
    |
    v
CPU 在小缓冲区绘制
    |
    v
LPSPI + DMA
    |
    v
带 GRAM 的屏幕控制器
```

这种方案适合评估小屏幕、局部数值、菜单和状态界面。

优势是：

- 主控侧可以只保留部分画面的绘制缓冲区。
- 接口引脚通常较少。
- 显示扫描主要由屏幕端完成。

限制是：

- 大面积持续更新容易遇到接口吞吐瓶颈。
- 图片处理和绘制仍可能占用较多 CPU。
- 屏幕端 GRAM 更新也需要考虑扫描同步。

RT1011、RT1021 等可以作为这种架构的候选，但是否达到目标体验，必须按实际画面和链路计算，不能只凭示例能够运行判断。

### 5.2 以显示控制器、外部 RAM 和 PXP 为中心

典型数据路径：

```text
CPU / PXP
    |
    v
主控可访问的完整帧缓冲区
    |
    v
显示控制器
    |
    v
RGB 面板
```

RT1052、RT1062、RT1064 等代表平台，可以用于研究这类路径。

这里的核心已经不只是“传得快不快”，还包括：

- 连续扫描所需的内存供数。
- 绘制与扫描是否争用同一存储系统。
- PXP 是否能处理目标操作。
- 帧缓冲区换帧与缓存一致性。

这种方案通常更适合大一些的显示区域，但也带来更多存储、布线和同步要求。

### 5.3 以 GPU、复杂图形和多种显示输出为中心

在已核对能力的 RT1166、RT1176 等平台上，可以进一步研究 GPU / 矢量图形、PXP、RGB 和 DSI。

这种平台为复杂图形提供更多执行选择，但并不意味着每个 GUI 都应该把所有模块同时用起来。

需要关注：

- GPU 对目标绘制任务的实际覆盖范围。
- 支持的输入、输出格式和内存布局。
- 提交、执行、同步与 Cache 维护开销。
- GPU、CPU、显示控制器之间的带宽竞争。
- 多核系统中对图形资源的访问和管理。

**模块更多，是选择空间更大，不是性能收益自动更多。**

## 6. 从具体需求做三次选型推演

以下都是架构推演，不是某块开发板的性能承诺。

### 6.1 场景 A：320 × 240，主要更新数值与状态

假设采用 RGB565。

完整一帧需要：

```text
320 × 240 × 2 = 153,600 B = 150 KiB
```

如果使用两块各 20 行的局部绘制缓冲区：

```text
320 × 20 × 2 × 2 = 25,600 B = 25 KiB
```

因此，对 128 KiB 级别的片上 RAM：

- 150 KiB 的完整主控帧缓冲区已经超出总容量。
- 25 KiB 的两块局部工作缓冲区在容量量级上更合理。
- 还必须扣除 GUI 堆、任务栈、字体缓存和其他业务数据。

如果屏幕带 GRAM，可以优先考虑“CPU 软件绘制 + 小缓冲区 + DMA 按区域发送”。

但需要另算接口吞吐。局部数值更新可行，不代表整屏转场也达到同样体验。

### 6.2 场景 B：800 × 480，需要较多页面动画

RGB565 的两个完整帧缓冲区需要：

```text
800 × 480 × 2 × 2 = 1,536,000 B = 1,500 KiB
```

与代表平台的片上 RAM 总量比较：

| 容量参考 | 能说明什么 |
| --- | --- |
| 512 KiB | 不足以容纳这两个完整帧缓冲区 |
| 1 MiB，即 1,024 KiB | 仍然不足 |
| 2 MiB，即 2,048 KiB | 总量上还剩 548 KiB，但不能据此认定方案已经可用 |

最后一种情况仍要回答：

- 两个帧缓冲区是否都位于显示和加速器可访问的区域？
- RAM 是否连续，或可按目标驱动要求分别分配？
- GUI 之外还有多少任务和工作数据？
- 动画是否需要额外的离屏图层？

这类场景应认真评估外部 RAM、显示控制器和适用的加速后端。

### 6.3 场景 C：800 × 480，复杂透明图层和图形变换

如果两个完整帧都采用 ARGB8888：

```text
800 × 480 × 4 × 2 = 3,072,000 B = 3,000 KiB
```

这已经超过 2 MiB。

同时，透明混合会读取前景和背景，再写入结果，内存访问量远大于只写一张纯色画面。

这里应同步评估：

1. 是否真的需要所有完整帧使用 ARGB8888。
2. 能否只给局部离屏图层保留 Alpha。
3. GPU / PXP 是否支持所需格式与操作组合。
4. 外部 RAM 是否提供足够的实际带宽。
5. LVGL 后端是否真正覆盖这些任务。

不应先购买“有 GPU 的芯片”，再假设它能消除所有容量和带宽问题。

## 7. 内存接口，决定资源能不能到达正确的地方

选型时，至少应区分三类存储用途：

| 用途 | 常见存储位置 | 核对重点 |
| --- | --- | --- |
| 程序、图片、字体等静态资源 | Flash 或其他非易失存储 | 容量、读取速度、资源格式和访问方式 |
| GUI 运行数据与工作缓冲 | 片上 RAM 或外部 RAM | 容量、峰值、碎片、访问延迟 |
| 显示与加速器使用的像素缓冲区 | 相关模块可访问的 RAM | 地址范围、格式、对齐、Cache 和带宽 |

特别要避免两个误解。

### 7.1 Flash 多，不等于帧缓冲空间多

Flash 适合保存程序和资源，但不能直接当作高频写入的普通帧缓冲 RAM。

资源放在 Flash，绘制或解码过程中仍可能需要 RAM；某些图形操作还会产生额外输出缓冲区。

RT1064 产品中的 Flash 容量，是资源和程序布局条件，不是 GUI 工作 RAM 的直接扩容。

### 7.2 CPU 能访问，不代表所有外设都能访问

CPU、DMA、显示控制器、PXP 和 GPU 不一定具有完全相同的内存访问路径。

对每块缓冲区都应核对：

```text
谁写入 -> 谁读取 -> 地址是否可达 -> 数据何时可见 -> 谁决定释放
```

不能只因为一段内存被称作 TCM 或 SRAM，就把它分配给所有像素消费者。

具体平台的访问限制与可配置方式，会在存储和 Cache 章节中进一步展开。

## 8. 屏幕接口选择，不能脱离平台选择

| 接口方案 | 优先评估的条件 | 典型代价 |
| --- | --- | --- |
| 单线 SPI + 屏幕 GRAM | 更新面积较小，或吞吐要求较低 | 大面积更新受串行吞吐限制 |
| 多数据线 QSPI 显示 | 面板协议与主控事务能力明确匹配 | 协议、驱动和资源共享更复杂 |
| 8080 式并口 | 可用引脚、时序与 DMA 路径合适 | 引脚和软件实现成本增加 |
| RGB 连续扫描 | 原生显示控制器和完整帧存储条件满足 | 连续内存带宽、时序和同步要求 |
| MIPI DSI | Host、PHY、面板模式与软件栈匹配 | 链路与面板配置复杂度较高 |

这里没有绝对的“高级接口优于低级接口”。

一个以局部数值为主的小屏幕，使用带 GRAM 的串行方案，可能比完整帧连续扫描更符合成本和内存目标。

一个持续整屏动画界面，则可能更需要高吞吐输出和稳定的帧存储路径。

此外，不同屏幕之间的价格、触摸方案、连接器和初始化支持，也会影响最终选择。

## 9. SDK 示例能证明什么，不能证明什么？

SDK 示例很有价值：它能帮助我们建立一个已知条件下的起点。

但示例的结论是有边界的。

一个 LVGL benchmark 示例能够运行，最多说明这一套平台、屏幕、存储、驱动和软件配置已经能够完成对应工作负载。

它不能自动证明：

- 另一块屏幕的初始化和时序相同。
- 更高分辨率仍满足内存和带宽条件。
- 所有控件都被硬件加速。
- benchmark 数字与真实产品场景等价。
- 更换 LVGL 主版本后，端口仍能原样使用。

正确的复用步骤是：

1. 记录示例的完整平台条件。
2. 确认显示和存储数据路径。
3. 保留能够稳定工作的基线。
4. 每次只改变与目标需求有关的一项条件。
5. 对正确性、资源占用和性能重新测量。

不要直接把示例的 FPS 写成该芯片的“GUI 性能”。

## 10. 本系列的实战平台怎样组织？

为了避免每篇都换一套环境，系列实战适合采用“基础路径 + 进阶路径”的组织方式。

| 路径 | 可考虑的代表平台 | 主要承载内容 |
| --- | --- | --- |
| 基础显示与像素处理 | RT1062 等已核对平台 | RGB、帧缓冲、PXP、存储与 Cache、LVGL 基线 |
| GPU 与 DSI 进阶 | RT1176 等已核对平台 | GPU / VG-Lite、DSI、复杂绘制任务与性能对照 |
| 小内存串行显示补充 | RT1011、RT1021 等 | 局部缓冲、GRAM、SPI 吞吐与 DMA |

这只是系列写作和实验组织建议，并不表示已经选定开发板，也不要求已有项目换板。

如果已经有另一块四位数型号的 i.MX RT 开发板，可以继续使用它。关键是补齐该平台的能力表和实验条件，不把其他型号的功能或成绩直接移植过来。

开始板卡相关实战前，至少固定：

- 芯片完整订货型号和开发板版本。
- 屏幕模组、控制器、接口与分辨率。
- 外部存储器型号和连接方式。
- SDK、LVGL、RTOS 和编译器版本。
- CPU、存储及显示相关时钟。
- 缓冲区布局和 Cache / MPU 属性。

## 11. 一张可以直接用于项目的选型卡

下面这张卡可以附在项目立项记录或文章实验条件中。

| 项目 | 待填写内容 |
| --- | --- |
| 目标界面 | 页面类型、动画、透明图层、中文字体 |
| 体验指标 | 可见更新目标、输入延迟目标、撕裂要求 |
| 屏幕 | 模组型号、控制器、接口、分辨率、方向 |
| 芯片 | 完整订货型号、封装、温度等级 |
| 显示链路 | 专用控制器或传输外设、DMA、同步事件 |
| 绘制路径 | CPU、PXP、GPU，以及不支持任务的处理方式 |
| 内存 | RAM 区域、帧缓冲容量、工作区和峰值预算 |
| 外部资源 | Flash / RAM 型号、总线、可访问性 |
| 软件 | SDK、LVGL、RTOS、驱动和工具链版本 |
| 证据 | 手册章节、勘误、原理图、示例和测量记录 |
| 尚未验证 | 未完成的能力、风险和后续验证步骤 |

填写后，再用四个门槛检查候选方案：

1. **连接门槛：** 屏幕确实能够接上，协议和引脚兼容。
2. **容量门槛：** 必需缓冲区和业务数据能够分配。
3. **吞吐门槛：** 输出、内存和绘制能力满足目标工作量。
4. **软件门槛：** 驱动、框架和同步策略可以可靠实现。

某一项没有通过，不能用另一项的高分抵消。

## 12. 小结：先选数据路径，再选型号

对 GUI 来说，好的选型不是单项规格最好，而是整条像素路径与产品目标相匹配。

- 小屏幕、局部更新，可以优先评估小缓冲区与屏幕 GRAM。
- 大面积连续更新，需要认真检查显示控制器、完整帧存储和带宽。
- 复杂图形，需要确认加速器的真实任务覆盖，而不是只看“GPU”字样。
- 多核、Flash 容量和高主频都很有价值，但不能代替内存访问和软件适配验证。

下一篇：[《选屏之前，先算清分辨率、显存与带宽》](03-memory-and-bandwidth.md)。我们把这里的容量和吞吐判断展开成可以逐项复算的预算表。
