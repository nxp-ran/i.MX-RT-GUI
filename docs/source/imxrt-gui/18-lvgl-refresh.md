# 第 18 篇：理解 LVGL 的刷新与绘制机制

> 系列：[i.MX RT 图形系统实战](README.md)
>
> 上一篇：[LVGL 最小移植](17-lvgl-minimal-port.md)
>
> 下一篇：[让 LVGL 使用 PXP / GPU](19-lvgl-acceleration.md)
>
> 本篇目标：以 LVGL 9.2.0 解释无效区域、绘制任务、模式与缓冲交接，不把内部实现当作跨版本稳定 API。

## 1. 修改控件后发生什么？

一个标签内容变化，通常经历：

```text
对象状态改变
   -> 标记需要重绘的区域
   -> 刷新周期处理区域
   -> 生成绘制任务
   -> 后端执行
   -> 显示驱动 flush
   -> 交回缓冲
```

控件更新次数、绘制任务数、flush 次数和可见帧数不是相同指标。

没有变化时，LVGL 可以没有像素任务，但显示控制器仍可能持续扫描。

## 2. 无效区域不只是对象尺寸

移动对象需要重绘旧位置和新位置，阴影、边框、抗锯齿和透明层也可能扩大范围。

区域可能合并，也可能因缓冲容量拆成多个块。

因此，不能只从业务变化“一个数字”推断只传几个像素。应记录实际刷新区域。

把全部屏幕持续标为无效，会抵消局部刷新优势。另一方面，错误缩小区域会留下旧内容。

## 3. 三种模式

| 模式 | 缓冲要求 | 行为 |
| --- | --- | --- |
| PARTIAL | 可小于完整屏幕 | 按区域/块绘制，再传输或复制 |
| DIRECT | 完整屏幕大小 | 在帧中对应位置更新脏区 |
| FULL | 完整屏幕大小 | 每轮重新绘制完整屏幕 |

模式决定 LVGL 怎样生成数据，不决定屏幕硬件怎样保存图像。

PARTIAL 接到连续扫描屏，通常要把结果放入完整显示帧；DIRECT/FULL 也需要与显示扫描同步。

## 4. 两块缓冲在不同模式中的意义

PARTIAL 双缓冲可以让一个块发送、另一个块绘制。

DIRECT 双帧则涉及脏区域在两帧中的一致性。LVGL 9.2.0 有相应的同步处理，驱动不能绕过它的生命周期。

FULL 双帧容易表达传统前后台，但付出整屏绘制流量。

| 场景 | 可先评估 |
| --- | --- |
| GRAM 小屏局部界面 | PARTIAL |
| 完整扫描帧、稀疏变化 | DIRECT＋正确同步 |
| 完整动画与简单内容一致性 | FULL |

这不是硬性选型。应比较实际对象、内存和输出路径。

## 5. stride、位置与指针

刷新回调提供区域和像素，但它们的布局随模式改变。

PARTIAL 中源通常是本块图像；DIRECT/FULL 中源可能是完整帧起始，区域只是更新范围。

读取实际 draw buffer 描述，并确认端口如何解释位置、stride、旋转和 offset。不要对所有模式统一追加 `y × screen_width` 偏移。

源块高度也可能不是固定行数，尾块应按真实区域处理。

## 6. Draw task 不一定是一条硬件命令

后端会评估任务类型、格式、混合和参数。

CPU 与硬件可能分别处理同一帧的不同任务；需要遵守任务间依赖。

不能在一个 GPU draw 函数返回时就认为整帧绘制结束，也不能把未完成任务的目标交给显示。

对外部驱动而言，保持框架的绘制与完成契约，比自己猜测内部任务状态可靠。

## 7. Flush 的结束到底是什么？

`lv_display_flush_ready()` 表示驱动完成本次缓冲交接，不是“显示调用已经返回”，更不是“人眼已经看到”。

异步发送时等源释放；帧切换时按显示控制器和端口契约确认旧帧安全。

LVGL 的刷新/flush 事件也可能反映提交结束，而非物理扫描完成。测量时必须读事件定义。

驱动支持等待回调时，可以按 OS 通知方式等待，避免忙等；不要混用两套互不一致的完成机制。

## 8. 观察而不干扰

记录无效区域、任务后端、flush 块、等待与完整周期。

| 观察 | 判断 |
| --- | --- |
| 改一处却重绘整屏 | FULL、布局影响或额外无效化 |
| 块数很多 | 缓冲较小、区域碎片 |
| 等待时间高 | 输出或同步瓶颈 |
| CPU 和 GPU 交替 | 任务覆盖或依赖，并不一定异常 |
| 有刷新事件但没有新像素 | 事件边界不等于有效更新 |

日志有开销，采样和计数应避免改变要测的刷新节奏。

## 9. 小结

LVGL 刷新是对象、区域、任务、缓冲与驱动契约共同作用的结果。模式选择要结合显示架构和真实工作量。
