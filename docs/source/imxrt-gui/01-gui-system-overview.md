# 第 1 篇：一个嵌入式 GUI 系统到底由哪些部分组成？

> 系列：[从点亮屏幕到高性能 GUI：i.MX RT 图形系统实战](README.md)
>
> 下一篇：[i.MX RT 图形能力与平台选型](02-platform-selection.md)
>
> 本篇目标：从一次界面更新出发，理解屏幕、显示外设、绘制单元、存储和 LVGL 的分工。
>
> 适用范围：以 i.MX RT 为背景介绍通用原理，不假设所有型号具备相同外设。本篇不涉及特定开发板初始化；容量与带宽数字均为理论计算，不是开发板实测。

## 1. 屏幕点亮了，GUI 就算做好了吗？

第一次接触嵌入式 GUI 时，我们往往从一块开发板和一块屏幕开始。

接好排线，下载示例，背光亮起，画面出现。再运行一个图形演示，按钮、文字和动画都动起来了，看起来整个显示系统已经完成。

但真正开始做自己的界面时，问题才逐渐出现：

- 换一块屏幕，原来的驱动为什么不能直接使用？
- 静态图片正常，动画一多为什么就卡顿？
- CPU 主频不低，为什么画面还是不流畅？
- 开启双缓冲，为什么仍然会出现撕裂？
- 芯片有 PXP 或 GPU，为什么 LVGL 的帧率没有提高？

这些问题看似分散，其实都指向同一件事：**GUI 不是一个独立模块，而是一条由多个模块共同完成的数据链路。**

在讨论寄存器、驱动和加速之前，先区分三个目标：

| 目标 | 主要验证什么 | 还不能说明什么 |
| --- | --- | --- |
| 点亮屏幕 | 供电、复位、背光，以及必要的初始化或扫描链路 | 不代表像素格式和所有时序都正确 |
| 正确显示图片 | 像素内容能够通过显示链路稳定呈现 | 不代表动态更新足够快 |
| 流畅运行 GUI | 绘制、传输、同步、输入和业务任务协同工作 | 仍需进一步验证资源占用与长期稳定性 |

尤其要注意：**背光亮了，不等于屏幕已经收到有效图像。**

本系列的目标，是从第一步一直走到第三步，并且知道每一步为什么能够工作。

## 2. 先看全景：GUI 系统里的七个角色

一个典型的嵌入式 GUI 系统，可以拆成以下角色。

| 角色 | 主要职责 | 典型内容 |
| --- | --- | --- |
| 应用逻辑 | 决定界面应该表达什么 | 温度数值、页面切换、告警状态 |
| GUI 框架 | 管理对象、布局、样式、事件与刷新 | LVGL |
| 绘制执行单元 | 把绘制任务变成像素 | CPU 软件绘制、适用的 PXP / GPU 操作 |
| 存储与缓冲区 | 保存资源、工作数据和像素 | RAM、外部存储、绘制缓冲区、帧缓冲区 |
| 显示输出链路 | 把像素送到屏幕端 | SPI、并口传输、显示控制器、DSI Host 等 |
| 屏幕端 | 接收像素并驱动面板显示 | 屏幕控制器、GRAM、面板驱动电路 |
| 输入设备 | 把用户操作交给软件 | 触摸、按键、旋钮 |

从逻辑上看，可以画成下面这张图：

```text
触摸 / 按键 / 旋钮
        |
        v
输入驱动 -> GUI 事件与应用逻辑
                    |
                    v
             LVGL 对象与布局
                    |
                    v
           无效区域与绘制任务
                    |
                    v
        CPU 软件绘制 / PXP / GPU
                    |
                    v
                像素缓冲区
                    |
                    v
          显示控制器 / 传输外设
                    |
                    v
            屏幕控制器 / 面板
```

这不是芯片内部总线连接图。它表达的是“谁负责什么”，而不是要求像素必须依次经过 CPU、PXP 和 GPU。

实际工程中，某些任务可能由 CPU 完成，另一些任务交给硬件处理；也可能先在一块缓冲区绘制，再经过格式转换或搬运，最后才进入显示链路。

**硬件加速是一种执行选择，不是所有 GUI 系统都必须经过的一道固定工序。**

## 3. 一个按钮，是怎样变成像素的？

假设界面上有一个按钮。应用程序关心的事情通常很简单：

- 按钮放在哪里？
- 显示什么文字？
- 使用什么颜色？
- 按下后执行什么操作？

但屏幕并不理解“按钮”。屏幕最终接收的是像素，或者能够写入像素的命令。

因此，中间必须发生一次转换。

### 3.1 GUI 框架描述“画什么”

LVGL 管理按钮对象、尺寸、位置、样式和事件。

当按钮状态改变，例如从松开变成按下，框架需要判断哪些区域受到了影响，并安排相应的绘制工作。

这些工作可能包括：

- 绘制背景和圆角。
- 绘制边框。
- 混合阴影或半透明图层。
- 读取字形并绘制文字。

一个按钮不一定对应一次硬件操作，也不一定只产生一个绘制任务。

### 3.2 绘制执行单元负责“算出像素”

绘制工作可以由 CPU 软件代码完成，也可能有一部分交给 PXP 或 GPU。

是否能够加速，取决于：

1. 芯片是否具有相应硬件。
2. 硬件是否支持当前操作、格式和参数。
3. 驱动是否具备所需能力。
4. GUI 框架的后端是否能够派发这个任务。
5. 数据位置、对齐和同步条件是否满足要求。

因此，“芯片有 GPU”与“这个按钮由 GPU 绘制”之间，还有一整条软件适配链路。

即使像素操作交给硬件，CPU 通常仍然需要处理事件、布局、任务提交、资源管理和同步。

### 3.3 显示链路负责“送出像素”

绘制完成后，像素还需要进入屏幕端。

这可能意味着：

- 通过 SPI 把一小块像素写进屏幕 GRAM。
- 通过并行接口更新屏幕的指定区域。
- 让显示控制器扫描一块完整帧缓冲区。
- 通过显示控制器与 DSI 链路向面板输出图像。

到这里，才进入真正的显示输出阶段。

> GUI 框架决定界面内容，绘制执行单元生成像素，显示链路负责把像素交给屏幕。三者不是同一个层次。

## 4. 理解屏幕，先分清两种典型架构

讨论屏幕时，大家常从 SPI、RGB 或 MIPI DSI 等接口名称入手。

这些名称很重要，但还有一个更能影响软件架构的问题：

**屏幕端能不能保存画面，还是需要主控持续提供像素流？**

下面用两种典型情况说明。它们是常见系统架构，不应被理解为所有接口与面板的绝对分类。

### 4.1 架构 A：屏幕端保存画面，主控按需更新

许多 SPI 或 8080 式接口屏幕，带有显示控制器及 GRAM。

GRAM 可以理解为屏幕端用于保存图像的存储区。主控把像素写进去后，由屏幕端控制器读取这些像素并驱动面板刷新。

```text
主控侧                              屏幕侧

绘制缓冲区 -> SPI / 并口传输 -> 屏幕控制器与 GRAM -> 面板
```

例如，只更新一个数值区域时，主控可以：

1. 设置目标窗口。
2. 发送该窗口对应的像素。
3. 等待传输链路不再使用源缓冲区。
4. 复用源缓冲区，准备下一次绘制。

如果画面没有变化，通常不需要反复传输整屏像素；屏幕端仍然可以按自己的扫描节奏刷新已有画面。

这类方案的优势，是主控不一定需要保存完整画面。

但这不意味着它“不需要显存”。完整图像可能保存在屏幕 GRAM 中，主控侧仍然需要绘制、解码或传输所用的缓冲区。

### 4.2 架构 B：主控保存画面，显示控制器连续扫描

常见 RGB 屏方案中，完整画面保存在主控可访问的帧缓冲区中，由显示控制器持续读取并输出像素时序。

```text
主控侧

CPU / 加速器 -> 帧缓冲区 -> 显示控制器 -> RGB 接口 -> 面板
```

在某些 DSI 视频模式系统中，还会包含 DSI Host 和 PHY：

```text
帧缓冲区 -> 显示控制器 -> DSI Host / PHY -> 面板
```

在这类连续扫描方案中，即使画面完全不变，显示链路通常仍然需要按面板要求持续工作。

GUI 可以不重新绘制，但显示控制器仍然在读取已有像素。

这带来两个直接结果：

- 系统需要可供显示控制器访问的完整帧数据。
- 显示扫描本身就会占用内存和总线带宽。

DSI 同时存在命令模式、视频模式及不同面板实现，不能仅凭“DSI 屏”三个字推断它的缓冲结构。

### 4.3 两种架构的关键差别

| 比较项 | 屏幕端保存画面 | 主控侧保存并连续扫描 |
| --- | --- | --- |
| 完整画面主要保存在哪里 | 屏幕控制器的 GRAM | 主控可访问的帧缓冲区 |
| 主控如何更新画面 | 向屏幕写入变化区域或整屏 | 修改帧内容，或提交新的帧缓冲区 |
| 静态画面时 | 通常可停止主控侧像素传输 | 通常仍需持续扫描输出 |
| 常见关注点 | 接口吞吐、窗口写入、传输同步 | 内存带宽、扫描时序、换帧同步 |
| 主控侧能否只使用小绘制缓冲区 | 通常可以，取决于驱动设计 | 可以，但通常还需完整显示帧缓冲区 |

真正决定架构的，是屏幕控制器、接口模式、显示控制器和缓冲方案的组合，而不是接口名称本身。

## 5. 三种容易混淆的“显存”

讨论 GUI 时，“缓冲区”“显存”“帧缓冲”经常被混用。

为了避免后续接入 LVGL 时产生误解，本系列使用以下约定。

### 5.1 绘制缓冲区：这一次往哪里画？

绘制缓冲区是绘制执行单元写入像素的目标。

它可能是一整屏，也可能只是几十行，或者某个待处理区域。

以 800 像素宽、RGB565、40 行为例，紧凑存储时：

```text
800 × 40 × 2 = 64,000 B = 62.5 KiB
```

这块缓冲区可以反复用于绘制不同区域，前提是前一位使用者已经不再访问它。

### 5.2 显示帧缓冲区：显示控制器从哪里取整帧？

在典型连续扫描方案中，显示帧缓冲区保存显示所需的一整帧图像。

它通常必须满足显示控制器的格式、地址、行跨度、对齐和访问权限要求。

绘制缓冲区与显示帧缓冲区可以是同一块内存，也可以分开：

```text
方案一：直接绘制

绘制执行单元 -> 完整帧缓冲区 -> 显示控制器

方案二：分块绘制后更新显示帧

绘制执行单元 -> 小绘制缓冲区 -> 拷贝 / 转换 -> 完整帧缓冲区
                                               |
                                               v
                                           显示控制器
```

第二种方案节省的是绘制工作缓冲的容量，不代表可以省掉连续扫描所需的完整帧数据。

### 5.3 屏幕 GRAM：屏幕自己保存了什么？

屏幕 GRAM 位于屏幕端，通常通过命令或像素写入事务访问。

它不一定能像普通 RAM 一样被 CPU 随机读写，也不应默认可以作为 PXP / GPU 的直接输出目标。

只有把数据路径和寻址方式核对清楚，才能判断是否需要中间缓冲或额外搬运。

一句话总结：

> 绘制缓冲区服务于“生成像素”，显示帧缓冲区服务于“扫描输出”，屏幕 GRAM 服务于“屏幕端保存画面”。它们可能配合使用，但不是同一个概念。

## 6. 算一笔账：800 × 480 到底需要多少内存和带宽？

现在用一个具体算例，看看为什么 GUI 经常受存储系统限制。

假设分辨率为 800 × 480，像素紧凑排列，不考虑行对齐、额外图层和工作区。

### 6.1 一帧有多大？

```text
帧大小 = 宽度 × 高度 × 每像素字节数
```

| 格式 | 每像素字节数 | 单帧字节数 | 单帧容量 | 两帧容量 |
| --- | --- | --- | --- | --- |
| RGB565 | 2 | 768,000 B | 750 KiB | 1,500 KiB |
| RGB888 | 3 | 1,152,000 B | 1,125 KiB | 2,250 KiB |
| ARGB8888 | 4 | 1,536,000 B | 1,500 KiB | 3,000 KiB |

这里使用：

```text
1 KiB = 1,024 B
1 MiB = 1,048,576 B
1 MB  = 1,000,000 B
```

RGB565 两个完整帧缓冲区已经需要 1,536,000 B，约 1.465 MiB。

这还没有加入：

- 程序数据、任务栈和堆。
- 图片、字体与解码缓存。
- 离屏图层和加速器工作缓冲。
- 实际行跨度、对齐或特定格式带来的额外空间。

实际工程中，应优先按下面的形式核算：

```text
帧缓冲大小 = 实际行跨度（字节）× 高度
```

不能仅根据像素名称假设所有硬件都支持紧凑存储。

### 6.2 每秒要处理多少像素？

假设 RGB565 图像每秒完整扫描 60 次：

```text
有效像素速率 = 800 × 480 × 60
             = 23,040,000 pixel/s

有效像素数据量 = 800 × 480 × 2 × 60
               = 46,080,000 B/s
               = 46.08 MB/s
```

这个数只是有效图像数据对应的量级，不等于完整接口预算，也不等于系统总内存带宽。

例如，在“每帧都完整写入一次外部帧缓冲，显示控制器再完整读取一次”的简化模型下：

```text
绘制写入：46.08 MB/s
显示读取：46.08 MB/s
两项合计：92.16 MB/s
```

如果还要读取图片、读取旧背景、执行透明混合或搬运中间缓冲区，访问量会继续增加。

接口侧也要另算。以 RGB 时序为例，像素时钟还要满足包含消隐区的总时序要求，不能只按有效像素数配置；消隐时间也不应直接等同为额外的有效像素内存读取量。

如果采用带 GRAM 的局部更新方案，则主控链路不一定需要每秒发送 60 个完整画面，应根据实际更新面积重新计算。

**分辨率、像素格式和更新方式，决定了系统必须承担的基础工作量。CPU 主频只是其中一个条件。**

## 7. 绘制完成，不等于屏幕已经显示

在一个异步显示系统里，至少要区分下面几个时刻：

1. 软件提交了任务。
2. 绘制或像素处理真正完成。
3. 下游不再访问某块源缓冲区。
4. 新画面进入实际扫描，并逐步变成可见像素。

这几个时刻可能相隔很远。

### 7.1 对带 GRAM 的屏幕

典型流程是：

```text
绘制区域 -> 启动传输 -> 传输链路释放源缓冲区 -> 屏幕扫描新数据
```

启动 DMA 不代表数据已经送完；源缓冲区可以复用，也不代表整块新图像已经被面板扫描显示。

具体实现需要核对 DMA、外设 FIFO 和总线完成事件的定义，判断什么时候源内存不再被使用，以及什么时候传输真正结束。

### 7.2 对连续扫描的屏幕

使用两个完整显示帧缓冲区时，一种典型流程是：

```text
显示控制器扫描 A
        |
        +-> CPU / 加速器在 B 中生成下一帧
                         |
                         v
                    请求切换到 B
                         |
                         v
               在控制器规定的时机生效
                         |
                         v
                确认 A 不再被扫描读取
                         |
                         v
                    A 才能重新使用
```

仅仅把 B 的地址写进寄存器，不一定说明旧的 A 已经立即释放。

实际换帧时机、事件定义和安全复用条件，必须依据目标显示控制器确认。

### 7.3 LVGL 为什么需要刷新完成通知？

LVGL 需要知道显示驱动何时完成了本次缓冲区交接，才能按对应刷新模式继续使用缓冲区。

在 LVGL 9.2 的显示接口中，可以通过 `flush_cb` 和 `lv_display_flush_ready()` 看到这一职责划分，具体语义应结合所选刷新模式和端口实现理解。

对于异步传输，不能刚启动硬件就提前通知完成；对于帧缓冲换帧，也不能忽略显示控制器仍在读取旧缓冲区的事实。

**完成通知本质上是在交接缓冲区所有权，不是通知“函数已经返回”，也不是宣告“整幅画面已经被人眼看到”。**

还有一个容易忽视的区别：

> 两块小绘制缓冲区，可以帮助绘制与传输重叠；两个完整显示帧缓冲区，可以用于前后台换帧。二者都叫“双缓冲”，但作用并不相同，也都需要正确同步。

## 8. 判断流畅度，不能只看一个 FPS

“这个 GUI 有多少帧？”是一个常见问题。

回答之前，应该先说明测量的究竟是哪一种帧率。

### 8.1 屏幕刷新率

屏幕刷新率描述面板扫描更新的节奏。

例如，屏幕以 60 Hz 扫描，并不意味着应用每秒生成了 60 张不同的画面。没有新内容时，它可能反复显示同一帧。

### 8.2 GUI 更新帧率

GUI 更新帧率描述软件完成界面更新的频率，但需要明确统计边界：

- 完成一次绘制？
- 完成一轮区域提交？
- 完成一次缓冲区换帧？
- 还是产生了一次实际可见的新画面？

这些数字不能直接混用。一个画面的分块刷新，也不应把每个小块都算成一整帧。

类似地，GUI 任务调用频率或定时器频率，并不等于有效更新帧率。

### 8.3 CPU 占用率

同样的画面更新速度，可能对应完全不同的 CPU 成本。

例如，一种实现使用 CPU 逐像素处理，另一种实现把可支持的操作交给硬件，两者 FPS 接近，但后者可能为通信、控制或其他任务释放更多 CPU 时间。

反过来，如果驱动一直忙等硬件完成，硬件虽然执行了像素操作，CPU 占用率也未必明显降低。

因此，不能只凭 FPS 判断硬件加速是否有价值。

### 8.4 输入到显示的延迟

用户触摸按钮后，要经历输入采样、任务调度、事件处理、绘制、传输或换帧，再到面板扫描和响应。

可以把关键路径概括为：

```text
输入采样
   -> GUI 调度与事件处理
   -> 绘制
   -> 传输 / 换帧及必要等待
   -> 扫描到目标区域
   -> 面板响应
```

一个平均帧率不错的界面，仍然可能因为排队、调度或换帧策略而让人感觉“跟手性”不好。

### 8.5 流水线为什么有帮助？

如果绘制和传输串行执行，处理一轮更新的时间近似为：

```text
T = T_draw + T_transfer
```

如果有独立缓冲区，硬件也允许两者重叠，在理想稳态下，处理吞吐的周期可能接近：

```text
T ≈ max(T_draw, T_transfer)
```

但这只是理想条件下的处理吞吐模型，不代表实际可见帧率。

内存争用、缓冲区同步、面板刷新率和传输能力都可能成为新的限制；流水线也不必然降低单次输入的显示延迟。

所以，一个完整性能结论至少应同时报告：

**更新帧率、CPU 占用率、内存占用，以及输入到显示的延迟。**

## 9. PXP、GPU 和 LVGL，到底是什么关系？

在 i.MX RT 图形开发中，这三个名字经常一起出现，但它们并不是互相替代的东西。

### 9.1 PXP：处理它所支持的像素任务

PXP 是 Pixel Processing Pipeline，即像素处理流水线。

它面向特定像素处理需求。具体型号或 IP 版本可能提供格式转换、混合、缩放、旋转等能力中的一部分，并附带格式、尺寸、对齐及组合限制。

介绍或使用 PXP 时，应从目标芯片的能力表出发，而不是先假设它能执行所有二维绘图。

PXP 也不负责管理按钮、页面、事件和布局。

### 9.2 GPU：执行受硬件和驱动支持的图形工作

本系列关注 GUI 中的二维图形加速，不把这里的 GPU 等同于桌面显卡。

某些二维 GPU 能够执行图像操作、路径绘制、变换和混合，但具体支持范围取决于硬件、驱动以及软件接口版本。

VG-Lite 则是相关软件 API / 驱动栈的一部分，不是一块叫作“VG-Lite 外设”的硬件。

### 9.3 LVGL：组织界面和绘制工作

LVGL 提供对象、布局、样式、事件和刷新机制，并通过相应绘制后端执行任务。

它可以使用软件绘制，也可以在支持的平台和版本组合上使用硬件加速后端。

一种常见情况是：支持的任务由硬件处理，其余任务由软件执行。这意味着评估收益时必须关注实际场景，而不能只看工程里是否打开了某个宏。

可以这样记忆：

| 名称 | 主要回答的问题 |
| --- | --- |
| LVGL | 界面是什么，哪些内容需要更新？ |
| CPU / PXP / GPU | 这些绘制或像素处理任务由谁执行？ |
| 显示控制器 / 传输接口 | 处理好的像素怎样送到屏幕？ |

### 9.4 不同 i.MX RT 型号不能一概而论

作为公开资料的例子，NXP 的 RT1060 产品页分别列出了 LCD 显示控制器和二维图形加速能力；RT1170 产品页则列出了 2D GPU 和 MIPI CSI / DSI。

这些信息可以作为理解平台差异的入口，但不能据此把不同产品中的加速器视为同一种 IP，也不能推断其他型号必然具备相同能力。

正式选型时，还要继续核对参考手册、封装、开发板连接、SDK 和 LVGL 适配。

下一篇会专门建立这张能力矩阵。

## 10. 把整条链路串起来：一次触摸如何改变画面？

假设界面上有一个温度按钮，触摸后需要切换显示状态。

一次典型交互可以分成下面几步：

1. **输入采集。** 触摸控制器或输入驱动报告触点与状态。
2. **事件处理。** GUI 任务处理输入，应用更新按钮状态或显示内容。
3. **确定重绘区域。** 框架判断哪些区域失效，需要重新生成像素。
4. **组织绘制任务。** 背景、文字、图片或混合等操作被安排执行。
5. **执行绘制。** CPU 或适用的硬件后端将结果写入目标缓冲区。
6. **完成数据交接。** 等待相关操作完成，并按实际数据流维护必要的内存可见性。
7. **提交显示。** 将区域像素写入屏幕，或按显示方案提交帧缓冲区。
8. **安全释放缓冲区。** 根据所有下游使用者的状态，决定哪些缓冲区可以复用。
9. **面板扫描与响应。** 更新区域逐步变成实际可见内容。

其中任何一步出现问题，都可能表现为“界面不对”：

| 现象 | 优先检查的方向 |
| --- | --- |
| 触摸后很久才变化 | 输入采样、任务调度、排队、绘制和换帧等待 |
| 某些区域仍是旧画面 | 无效区域、Cache 可见性、更新区域和缓冲区交接 |
| 动画中出现横向断层 | 扫描与写入冲突、换帧时机、GRAM 更新同步 |
| 大面积更新时卡顿 | 绘制量、接口吞吐、内存带宽和同步开销 |
| 启用加速后偶发异常 | 地址可访问性、格式、对齐、缓存与异步生命周期 |

这张表给出的是排查方向，而不是根据现象直接下结论。真正定位时，仍需沿着数据路径采集证据。

## 11. 第一个观察实验：不改界面，先找出像素的去向

本篇先不写一套与具体开发板绑定的初始化代码，而是给出一个可以用于现有显示示例的观察实验。

本节提供验证方法，不预设任何板卡上的实测结果。

### 11.1 准备三个场景

| 场景 | 操作 | 主要观察点 |
| --- | --- | --- |
| A | 显示固定纯色或色条 | 基本显示链路、像素格式和稳定性 |
| B | 显示静止的 GUI 页面 | 无变化时是否重绘，显示链路是否仍持续工作 |
| C | 只让一小块区域变化 | 实际重绘范围、实际传输范围与同步方式 |

### 11.2 回答六个问题

1. 屏幕端是否带有保存画面的 GRAM？
2. 绘制目标缓冲区位于哪里，是整屏还是局部？
3. 如果存在显示帧缓冲区，它是否与绘制缓冲区共用？
4. 谁在读写这些缓冲区，相关硬件是否都能访问？
5. 软件根据哪个事件判断本次交接已经完成？
6. 没有画面变化时，CPU、接口和显示控制器分别在做什么？

可以结合显示驱动、链接布局、目标芯片手册和面板资料回答这些问题。

### 11.3 如何采集证据？

- 在绘制、传输启动和完成处记录时间，避免只统计一个外层函数。
- 在条件允许时，用 GPIO 标记关键时段，并用示波器或逻辑分析仪观察。
- 检查静态画面时接口是否继续输出，以验证对显示架构的理解。
- 查看实际执行的绘制后端，而不是只看功能是否被编译进去。
- 记录更新区域和传输区域，确认局部更新是否真正减少了工作量。

例如，在典型 RGB 连续扫描方案中，即使页面静止，像素时钟和扫描仍可能持续；而带 GRAM 的按需更新方案，在没有内容变化时，主控侧像素传输通常可以停止。

这两种现象都可能是正常设计，不能仅凭“总线一直在动”判断软件存在重复刷新问题。

完成这个实验后，应该能够画出自己的实际数据路径：

```text
资源在哪里？
    |
    v
谁把资源变成像素？
    |
    v
像素写到哪块内存？
    |
    v
谁继续读取这块内存？
    |
    v
通过什么链路到达屏幕？
    |
    v
什么事件允许复用缓冲区？
```

## 12. 几个最容易带偏后续设计的误区

| 误区 | 更准确的理解 |
| --- | --- |
| 主频高，GUI 一定快 | 系统还可能受接口、内存、同步和工作负载限制 |
| 显示控制器负责把控件画出来 | 它主要负责像素输出，不能替代 GUI 绘制 |
| 有 GPU，所有任务都能加速 | 需要硬件、驱动、框架后端和任务参数同时匹配 |
| 双缓冲必然无撕裂 | 还要满足正确的同步、换帧和所有权管理 |
| 带 GRAM 的屏幕不需要内存 | 画面保存在屏幕端，主控仍可能需要多种工作缓冲 |
| 刷新回调返回就能覆盖缓冲区 | 异步消费者可能仍在读取它 |
| 60 Hz 屏幕等于 GUI 60 FPS | 面板可以重复扫描同一帧，统计边界也可能不同 |
| 开启 Cache 只影响速度 | 非一致性系统中还会影响 CPU 与外设看到的数据 |

这些误区不是术语上的小问题。它们会直接影响内存预算、驱动实现和性能判断。

## 13. 小结：先建立系统模型，再讨论加速

一个嵌入式 GUI 系统，可以用三句话概括：

1. **应用与框架决定画什么。**
2. **CPU 或硬件后端负责生成、处理像素。**
3. **显示链路把像素交给屏幕，并按正确时序完成显示。**

贯穿这三件事的，是内存容量、带宽、数据一致性和缓冲区所有权。

当我们知道像素保存在哪里、由谁读写、什么时候能够复用，屏幕接口、显示控制器、PXP、GPU 和 LVGL 就不再是几个孤立的名词，而是一套可以逐层理解、验证和优化的系统。
