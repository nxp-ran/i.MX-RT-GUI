## 1. 内存不是一个可以任意分配的大数组

芯片标称的 RAM 总量，可能分布在不同区域。程序、堆、任务栈、其他内核和外设也会使用它。

CPU 能访问一块内存，不代表显示控制器、PXP、GPU 和 DMA 都能访问；访问延迟和 Cache 属性也可能不同。

因此，每块缓冲区都需要回答：

```text
保存什么 -> 谁写 -> 谁读 -> 放在哪里 -> 如何交接 -> 何时释放
```

只算“分辨率乘以像素字节数”，还不足以设计完整 GUI。

## 2. 三类存储，各有职责

| 存储 | 适合的用途 | 选型时要核对 |
| --- | --- | --- |
| 片上 RAM | 任务、控件状态、热点数据、小缓冲 | 分区、内核归属、外设可达性 |
| 外部 SDRAM / PSRAM | 大帧、图层、解码工作区 | 控制器兼容、时序、容量、实际吞吐 |
| Flash / 非易失存储 | 程序、图片、字体、配置 | 读取路径、XIP 竞争、资源格式 |

Flash 中存有图片，不代表可以把文件地址直接当作所有加速器的图像输入。

某些资源能映射读取，另一些必须经过文件系统和解码。压缩文件大小也不是解码后 RAM 大小。

TCM、OCRAM 等名称表达的是具体存储区域，不能替代目标芯片的访问矩阵。

## 3. 先列访问矩阵，再安排地址

用实际手册和链接布局填写以下表，而不是预先把所有格子设为可访问：

| 数据 | 生产者 | 消费者 | 必须核对 |
| --- | --- | --- | --- |
| GUI 对象与任务栈 | CPU | CPU | 堆栈容量、并发与峰值 |
| 局部绘制缓冲 | CPU / 绘制后端 | 传输外设或复制单元 | DMA 可达、stride、Cache |
| 显示帧 | CPU / PXP / GPU | 显示控制器 | IP 地址、格式、对齐、生命周期 |
| 图片与字体 | Flash / 解码器 | CPU / 后端 | 编码、解码、缓存与支持格式 |
| GPU 工作区 | 驱动 / GPU | 驱动 / GPU | 特定分配器与可见性要求 |

地址转换应沿用 SDK 的 CPU-to-IP 机制。一个有效的 CPU 指针不一定就是寄存器需要的地址值。

多核共享数据还要核对权限、访问路径和同步。不能只给双方同一个指针就宣布共享成立。

## 4. 容量预算必须统计同时存在的分配

假设 800 × 480、RGB565 双显示帧，并且独立保留局部绘制缓冲：

| 项目 | 假设配置 | KiB |
| --- | --- | --- |
| 显示帧 | 800 × 480 × 2 B，两块 | 1,500 |
| 绘制工作缓冲 | 800 × 40 × 2 B，两块 | 125 |
| 临时图层 | 200 × 100 × 4 B | 78.125 |
| 解码工作区 | 假设 | 64 |
| 图片和字体缓存 | 假设 | 128 |
| GUI、应用、任务栈 | 假设 | 256 |
| 合计 | 不含额外余量 | 2,151.125 |

2 MiB 等于 2,048 KiB，这份预算已经超出。

如果绘制直接进入完整帧，就不应重复计入相同的绘制分配。反过来，如果临时图层与解码缓存同时存在，就不能用“不会一直使用”把它们漏掉。

预算以最坏的同时存在场景为依据，不以平均堆占用为依据。

## 5. 布局的三个实际问题

### 5.1 对齐与行跨度

按控制器和后端要求计算 stride、首地址和分配步长。像素区之后的 padding 也属于分配范围。

缓存行隔离可能要求比图像格式更严格的边界。不要让像素与无关控制变量共享会被维护的缓存行。

### 5.2 碎片与动态对象

反复创建控件、解码不同尺寸图片和生成图层，可能让总空闲量足够而大块分配失败。

固定帧缓冲适合启动时预留；可变资源需要明确释放、容量上限和失败策略。不能把所有对象永久缓存作为默认解决方案。

### 5.3 外部存储初始化顺序

外部 RAM 未初始化之前，不应让启动代码、堆或驱动访问它。

若链接脚本把零初始化段放在外部 RAM，必须确认启动与存储初始化机制配合正确。改变一个数组的 section，并不是完整的存储迁移。

## 6. 带宽按访问路径分别统计

连续扫描 800 × 480、RGB565、60 Hz，有效读取量约 46.08 MB/s。

同样频率的完整 CPU 写入再增加 46.08 MB/s。图片复制、透明混合和中间结果会产生更多读写。

```text
外部 Flash --资源读取--> CPU / 解码
                              |
                              v
外部 RAM <---绘制读写--- CPU / PXP / GPU
    |
    +---扫描读取---> 显示控制器
```

每条总线单独预算。不同接口的 MB/s 不能简单相加后与其中一条总线的峰值比较。

XIP 取指和资源读取共享接口时，资源访问也可能影响 CPU。Cache 命中率、突发和等待要在真实场景下测量。

## 7. 一段容量复算脚本

这只是静态预算，不验证真实 RAM 地址或分配器：

```python
allocations = {
    "display_frames": 800 * 480 * 2 * 2,
    "draw_buffers": 800 * 40 * 2 * 2,
    "temporary_layer": 200 * 100 * 4,
    "decoder": 64 * 1024,
    "resource_cache": 128 * 1024,
    "application_and_stacks": 256 * 1024,
}
capacity = 2 * 1024 * 1024
total = sum(allocations.values())

print(f"Allocated: {total:,} B ({total / 1024:.3f} KiB)")
print(f"Capacity: {capacity:,} B")
print(f"Shortfall: {max(total - capacity, 0):,} B")
```

输出：

```text
Allocated: 2,202,752 B (2151.125 KiB)
Capacity: 2,097,152 B
Shortfall: 105,600 B
```

这里显示缺口，而不是用默认值宣告方案可行。真正的分配失败必须通过项目错误通道报告。

## 8. 用三个实验验证布局

| 实验 | 操作 | 观察 |
| --- | --- | --- |
| 静态扫描 | 固定帧，不运行动画 | 基础扫描和错误计数 |
| 资源压力 | 反复进入峰值资源页面 | 堆峰值、大块分配、释放 |
| 综合压力 | 动画、解码、通信共同运行 | 带宽、等待、欠载、延迟 |

分别记录片上/外部 RAM 占用、堆和栈峰值、分配失败以及访问异常。

若某区“更快”，还要验证它对全部消费者可达、缓存处理正确，并且没有牺牲其他实时任务。

## 9. 小结

内存设计要同时通过容量、可达性和吞吐三个门槛，并落实到真实的链接与启动顺序。
